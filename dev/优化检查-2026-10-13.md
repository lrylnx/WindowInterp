# WindowInterp 优化检查（2026-10-13）

本轮直接检查 main.swift、build.sh，以及此前的引擎、延迟和功耗实测记录。没有修改插帧引擎或强行改变倍率、画质和队列深度。

## 已完成

- 亮度诊断从每个完整帧一次降到每秒最多两次。60fps 时像素缓冲锁定及 CPU 亮度采样次数理论上减少约 96.7%；这不是帧率提升百分比。
- 渲染循环每帧使用 autoreleasepool，及时释放临时 Core Image / Metal 对象，限制长期运行时临时对象积累。
- 为跨线程读取的渲染帧数、替换帧数、采集帧率、截图图像、输出尺寸和重建设置加锁；停止后回调再次检查状态，避免新帧重新进入已停止的管线。
- 连续两秒没有渲染新帧时采集帧率归零，避免画面已经冻结却仍展示上一次帧率。
- 启动增加代次检查，防止重复启动、取消后旧异步任务重新打开输出窗口；启动期间按钮显示“取消启动”。保留暂停后的重新采集路径。
- 启动失败或当前捕获流中断会清理采集和覆盖层；已停止流的错误回调被忽略，旧会话的回调不影响新会话。
- 未运行时每秒状态刷新不再覆盖失败及权限提示；无帧提示按本次启动时间计算。
- HUD 不再将采集帧率乘倍率冒充输出数据。引擎统计缺失或超过四秒未更新时显示等待状态，统计推算出的输出明确标为估计值。
- 修正 ARGB 亮度诊断通道顺序。
- 构建脚本在外部播放器资源缺失时复用 App 内已有且非空的引擎文件。
- 暂停测试只安排一次，防止恢复后反复创建暂停测试定时任务。

`python3 dev/verify-2026-10-13.py`：测试源成功创建，但 App 未获系统屏幕录制权限，目标枚举失败（TARGET_NOT_FOUND）。未实际进入采集，不能将退出码 0 当成运行测试通过。日志保存在 dev/verification-2026-10-13/。本轮未验证实际帧率、端到端延迟、暂停恢复或覆盖层视觉效果。

## 下一步建议

1. 授予本项目 App 屏幕录制权限，退出再打开，然后运行验证脚本；以浏览器全屏视频、游戏和多显示器分别测帧率、帧间隔 p95、延迟 p50/p95。用相同输入与设置比较备份版和新版，至少重复三轮。
2. 延迟优化重点应继续放在倍率规划。此前实测显示多个引擎环境开关收益落在噪声范围内，高倍率虽然贴近显示刷新率，却会压低采集上限、增加交互迟滞。游戏和视频需要分别评估，不能只追求输出统计数字。
3. 主线程仍定期查询窗口位置，覆盖层跟随为轮询；快速拖动与跨屏移动值得单独测试，再考虑事件驱动或拖动期间提高跟随频率。
4. updateSize 的配置更新仍通过独立 Task 提交。快速缩放时需要实测是否存在旧尺寸配置覆盖新配置，再决定是否改为串行合并更新。
5. 本地引擎以二进制 dylib / DLL 形式存在，主屏刷新率排程和多屏输出的改善需要引擎层配合。当前不能仅凭宿主代码承诺降低显示排程延迟。
6. UI 可进一步将采集帧率、估计输出和延迟实测分开显示，并增加丢帧及失联状态。当前优先修正了误导数值与启动/失败状态，大幅外观重做未包含在本轮。
