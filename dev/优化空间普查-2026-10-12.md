# 优化空间普查 — 延迟 / 画质 / 流畅度 / 补帧效果

日期：2026-10-12 · 机器：M4 / macOS 15.8.1 · 主屏 Q24T09 2560×1440@144Hz
方法：`dev/engine-probe.sh`（新写）—— 不起截图延迟法，直接读引擎自报统计。
源：testpattern 1280×560 · 光流 1.0 · 工作分辨率跟随源像素 · 每轮 16 s。
一个刷新周期 = **6.944 ms**。

结论一句话：**延迟已经封死（只剩倍率一个杠杆），但画质和帧节奏都还有真金 —— 而且你现在
这套「5×」配置，恰好是"延迟最差、但节奏最顺"的那一端。**

---

## 一、延迟：6 个引擎旋钮全部实测无效

同一条件（2× / 光流 1.0 / 源 1280×560）逐个加旋钮，看引擎自报的延迟分解：

| 旋钮 | 原帧 `enqueue_display` p50/p95 | 生成帧 p50/p95 | `generated`/60源帧 | 判定 |
| --- | --- | --- | --- | --- |
| 基准（无附加） | 29.2 / 32.8 | 22.2 / 25.7 | 898 | — |
| `LSFGM_OVERRIDE_PRESENT_MODE=0` | 29.0 / 32.0 | 21.6 / 25.4 | 898 | **无效** |
| `LSFGM_PERFORMANCE_MODE=1` | 28.5 / 32.1 | 21.6 / 25.1 | **857** | 无效，且**掉产 4.6%** |
| `LSFGM_PACING_MODE=adaptive` | 29.5 / 32.2 | 22.5 / 25.0 | 898 | **无效**（但**没有**像旧记录说的那样失效） |
| `LSFGM_PRESERVE_SWAPCHAIN_IMAGE_COUNT=3` | 29.0 / 32.4 | 22.0 / 25.5 | 898 | **无效** |
| `LSFGM_NO_FP16=1` | 29.4 / 32.8 | 22.4 / 25.9 | **839** | 无效，且**掉产 6.6%** |

全部落在噪声内（±1 ms）。原因在分解里写得很清楚：

```
queue_ms=0.007~0.021   worker_ms=0.16~0.46   drawable_ms=0.008~0.075   ← 全是 0.x ms
submit_display_ms=21~28                                             ← 99% 在这
```

**「等 vblank 上屏」这一步占了 99% 的延迟，而它由排程器决定，没有任何旋钮能碰。**
⇒ 唯一杠杆是**倍率**和**刷新率**；144Hz 已是这块屏的上限（`dev/list-modes` 里 2560×1440
只有 60/75/120/144 四档）。

### 顺带订正一条旧记录
README 里写着「`LSFGM_PACING_MODE=adaptive` 会让插帧**静默失效**」。本轮复测**未复现**：
adaptive 下 `generated` 正常增长（898/60 源帧），还多出 `slots=2:60` 标记，说明它确实
接管了节奏分配；**只是延迟一点没降**，`worker_ms` 反而从 0.32 降到 0.16。
（旧结论可能是早期版本或不同路径下测的，保留两种记录。）

## 二、真正被忽略的那个量：**帧节奏（`late`）**

引擎自报 `Metal display intervals=240 p50_ms=6.945 p95_ms=… late=N`：
`p50 = 6.945 ms` 恰好是**一个刷新周期**（144Hz），说明中位数每 vblank 送一张 —— 合格。
但 `late` 是**「间隔超过一个周期的帧数」**，它随倍率剧烈变化：

| 倍率 | 实测源 fps | 输出 fps | `144 ÷ 输出` | `late`/240 | 生成帧 `enqueue_display` p50/p95 | `worker_ms` p95 |
| --- | --- | --- | --- | --- | --- | --- |
| **2×** | 57 | 114 | **1.26** | **62（26%）** | 20.6–22.2 / 23.4–25.7 | **0.5** |
| **3×** | 46 | 138 | 1.04 | 9（3.8%） | 23.2–24.8 / 29.2–30.1 | 3.0 |
| **5×** | 29 | 145 | **0.99** | **1（0.4%）** | 27.6–32.8 / 39.6–46.5 | **20** |

### 规律（本轮最重要的发现）
**`late` 由「刷新率 ÷ 输出帧率」是否接近整数决定。**

* 输出帧率能整分刷新率（每帧占 k 个 vblank）⇒ 节奏完全规整 ⇒ `late ≈ 0`
* 不能整除 ⇒ 一部分帧要挤两个周期 ⇒ `late` 抬升到与之匹配的比例

三条数据严丝合缝：

* 2×：144/114 = **1.26** ⇒ 约 26% 的帧挤到 2 个周期 ⇒ 实测 26% ✓
* 3×：144/138 = 1.04 ⇒ 4% ⇒ 实测 3.8% ✓
* 5×：144/145 = 0.99 ⇒ 0% ⇒ 实测 0.4% ✓

### 为什么高倍率反而"顺"
因为 `autoMatchFPS`（`main.swift` 的 `effectiveCaptureFPS`）把采集帧率钳到
`刷新率 ÷ 倍率`：

```
2×: budget = 144/2 = 72，源 57 < 72  ⇒ 不钳  ⇒ 输出 114  ⇒ 1.26 个周期/帧 ⇒ late 26%
3×: budget = 144/3 = 48，源 57 > 48  ⇒ 钳到 46 ⇒ 输出 138 ⇒ 1.04           ⇒ late 3.8%
5×: budget = 144/5 = 29，源 57 > 29  ⇒ 钳到 29 ⇒ 输出 145 ⇒ 0.99           ⇒ late 0.4%
```

**倍率越高，钳制越狠，输出越贴近刷新率，节奏越规整。** 代价是两条：

1. **延迟**：生成帧 `enqueue_display` 从 2× 的 20.6 ms 涨到 5× 的 27.6–32.8 ms；
2. **`worker_ms` 长尾**：2× 的 p95 是 0.5 ms，**5× 是 20 ms（40 倍）** —— 光流偶尔很慢，
   这是「5× 看起来发飘 / 偶发一顿」的来源。

### ⚠️ 陷阱：5× 会把源砍半
`effectiveCaptureFPS` 的下限是 24。5× 时预算 29 fps：

* **24 fps 视频**：24 < 29 ⇒ 不钳 ⇒ 24×5 = 120 fps，144/120 = **1.2 ⇒ 节奏不整**（5× 白瞎）
* **60 fps 游戏**：60 > 29 ⇒ **砍到 29** ⇒ 源信息量掉一半 ⇒ 插出来的帧是低信息帧之间的插值
  ⇒ 动起来迟滞。**这就是「游戏模式一丝帧率都没提升、反而更卡」的根因** —— 不是引擎算不动
  （实测 5× 完美达产 145 fps），是**源在采集侧就被砍了**。

## 三、画质：还有真金，但要付代价

| 手段 | 现状 | 实测代价 | 建议 |
| --- | --- | --- | --- |
| **光流 `0.5 → 1.0`** | 你现在是 **0.5**（UI 标「省电推荐」） | 实测对延迟几乎无影响（生成帧 20.6 → 22.2 ms，边缘噪声） | ✅ **值得调回 1.0**，代价主要在功耗（算力随 flow_scale 平方） |
| `LSFGM_PERFORMANCE_MODE=1` | 未开 | **掉产 4.6%** | ❌ 别开 |
| `LSFGM_NO_FP16=1`（关半精度） | 未开 | **掉产 6.6%** | ❌ 别开（画质收益未量化，但先没了 6.6% 帧） |
| 工作分辨率 | 已是最高（跟随源像素） | — | 无空间 |
| **端到端色彩管线** | **sRGB 8 bit 硬编码** | 见下 | ⚠️ 唯一没探索的大块 |

### 色彩管线：天花板在 8 bit sRGB
三处全部写死（`main.swift`）：

```
575/609  config.pixelFormat     = kCVPixelFormatType_32BGRA     ← 采集
576/610  config.colorSpaceName  = CGColorSpace.sRGB
1500     metal.pixelFormat      = .bgra8Unorm                   ← 输出层
1509     metal.colorspace       = CGColorSpace.sRGB
684      colorSpace:            CGColorSpace(name: sRGB)         ← 渲染
```

⇒ **任何 Display P3 / 10 bit HDR 的源，都在采集第一步被压成 8 bit sRGB**，色域和灰阶精度
都丢在这里。而引擎里明明备着两套生成着色器：

```
mipmaps generate_8bit generate_16bit  ← 99 个着色器里的两个
```

**本工具永远只走 `generate_8bit`** —— `generate_16bit` 从未被使用过。
理论上把采集换成 10 bit（如 `kCVPixelFormatType_ARGB2101010LEPacked`）、输出层换
`.bgra10_xr_srgb` / `.rgba16Float`、色彩空间换 Display P3，就能接上 16 bit 生成路径。
**但这是一处会触发引擎像素格式校验的改动**（引擎日志里有
`Frame generation disabled for this Metal layer (pixel format …)` / `unsupported drawable
pixel format` 两条分支）—— 改错会让插帧**静默关掉**。**属于"有空间但要谨慎验证"的一类，
本轮只做可行性判定，未动手。**

## 四、配置文件：一个从没启用过的能力

引擎支持 `conf.toml`，存在性检查过：

```
/etc/lsfg-metal/conf.toml            ← 不存在
~/.config/lsfg-metal/conf.toml       ← 不存在
LSFGM_CONFIG（可用环境变量指定路径）
```

它支持的键（从 dylib 的解析错误串里挖出）：`multiplier` / `flow_scale` / `pacing_mode` /
`performance_mode` / `override_present_mode` / `preserve_swapchain_image_count` /
`log_file` / `log_level` / `dll`，并且**支持按应用分档**：

```
profiles · kind · fallback · active_in · executable name · Steam App ID · catch-all profile
```

⇒ 可以做到「看视频的 App 用 5×、游戏用 3×、其他用 2×」，**自动切换，不用每次进菜单改**。
这是目前**最实用、零风险**的一块未开发空间。

## 五、架构级的两条路（不是旋钮）

1. **把 `lsfg-metal` 注入 CrossOver 容器**（`DYLD_LIBRARY_PATH` 冒充 libMoltenVK +
   `LSFGM_METAL=1`）：省掉采集环 ⇒ 延迟更低、10 bit/HDR 无损、**输入透明所以真能玩游戏**。
   本机**未装 CrossOver**。（这是"小黄鸭式跟手"在 Mac 上的正解。）
2. **macOS 26 的 `VTLowLatencyFrameInterpolation`**（苹果原生低延迟插帧）：需要 macOS 26+，
   本机 15.8.1 用不了（`VTFrameRateConversion` 15.4+ 可用，但不是低延迟那条）。

## 六、可操作清单（按性价比排序）

1. **看 24 fps 视频别用 5×**：24×5 = 120，144/120 = 1.2 ⇒ 节奏不整。
   24 fps 的**最佳倍率是 2×（48 fps，144/48 = 3 整）或 3×（72 fps，144/72 = 2 整）**。
   —— 这正是你说的「原视频更流畅、插帧更卡」的来源。
2. **游戏用 3×，不是 2×**：60 fps 源下 3× 会被钳到 48 ⇒ 输出 138–144 ⇒ `late` 从 26% 掉到
   3.8%，代价只有 +2.6 ms 延迟；2× 不钳源帧但节奏最差。
3. **光流调回 1.0**：对延迟几乎无影响，画质白赚（代价是功耗）。
4. **建 `~/.config/lsfg-metal/conf.toml` 做 per-app 分档**：一次配好，之后自动切换。
5. 别开 `PERFORMANCE_MODE` / `NO_FP16`：实测掉产 4.6% / 6.6%。

**未做但可做**：16 bit/P3 色彩管线（要改采集+输出，有静默失效风险）；
把屏幕切到 **120 Hz** 做"匹配友好"验证（120 能被 24/30/40/60 整除）—— 本轮**未实测**，
仅由 `late` 规律推得。

## 复现

```sh
cd ~/Documents/WindowInterp
dev/engine-probe.sh <标签> <倍率|off> <工作分辨率|0> <光流> <源宽> <源高> [额外 KEY=VALUE ...]

# 例：复现"倍率 vs 帧节奏"
dev/engine-probe.sh m2x 2 0 1.0 1280 560 LSFGM_LATENCY=1     # ⇒ late 26%
dev/engine-probe.sh m3x 3 0 1.0 1280 560 LSFGM_LATENCY=1     # ⇒ late 3.8%
dev/engine-probe.sh m5x 5 0 1.0 1280 560 LSFGM_LATENCY=1     # ⇒ late 0.4%
```

整轮输出落盘 `/tmp/probe-<标签>.out`。原始数据本轮全部保留在 `/tmp/probe-*.out`。
