# 缩放与画质增强（FSR / Anime4K 那种）—— 可行性评估

2026-10-12 第十四轮之后。用户问：

> 有没有办法实现 小黄鸭那种 带 anime 4k、fsr 那种缩放？它是窗口化用那种缩放技术，把窗口最大化，
> 比如 720P 的窗口，fsr 缩放到满屏分辨率。

**结论先给：可以做，而且我们缺的只有一环**（渲染链中间那道「放大重建」），
下游的 LSFG 插帧、点击穿透、4Hz 跟随**都不用动**。
但有**一个架构分岔必须用户拍板**，选错了会把第十三轮刚删掉的那类东西请回来（见 §3）。

---

## 1. 小黄鸭（Lossless Scaling）到底有哪些缩放档

官方（losslessscaling.com）列的**空间缩放**算法：

| 档位 | 性质 | 适用 |
| --- | --- | --- |
| **LS1** | THS 自研，ML 模型 | 现代 3D 游戏（画质/性能比最好） |
| **AMD FSR** | FSR **1.0**，开源 | 3D 游戏，A/N 卡通吃 |
| **NVIDIA Image Scaling** | NIS | N 卡 |
| **Integer Scaling** | 整数倍 | 像素艺术 / 复古 |
| **Nearest Neighbor** | 最近邻 | 极低开销 |
| **xBR** | 像素画平滑 | 2D 手绘 |
| **Anime4K** | 轻量 ML，强化线条与色彩 | **动漫 / JRPG / 卡通** |
| **Sharp Bilinear / Bicubic** | 插值 + 锐化 | 通用 |
| **CAS** | AMD 对比度自适应锐化 | 纯锐化 |

几条官方/实测的硬事实，直接决定我们的方案：

1. **独占全屏无效** —— LS 只能处理窗口化 / 无边框窗口。这一点跟我们**完全同构**
   （我们就是抓窗口 + 覆盖层），所以它的做法对我们有直接参考价值。
2. **LS 的「FSR」档是纯锐化、不动态降分辨率**（实测教程原话：「小黃鴨的 FSR 是 1.0 版，
   純銳化不動態降解析度」，评价是「遠景清晰度比遊戲內建的 DLSS 或 FSR 更舒服」）。
   **这条最关键**：说明 LS 是把源 App **已经放大过**的画面拿来做重建/锐化，
   **不是**自己去改源 App 的分辨率。⇒ 我们不需要去动源 App。
3. 缩放与插帧是**两个正交的开关**（LS 里分别勾）。我们同理：可以只加缩放、不开插帧。

## 2. 我们现在的管线，以及缺口在哪

```
源窗口 ──SCStream采集──> CIImage ──CIContext 直线缩放(双线性)──> drawable ──LSFG hook──> 上屏
```

- `CapturePipeline.present(_:)`（`main.swift:874`）现在做的事情是：
  `context.render(transformed, to: drawable.texture, bounds: renderSize)` ——
  `transformed` 只是一次 `CGAffineTransform` 缩放，**滤镜就是双线性**。
  这正是 LS 要替掉的那个「GPU 驱动双线性缩放」。
- `metal.drawableSize = captureSize`（`main.swift:1811`）、`renderSize` 由
  `plannedCaptureSize(for:)` 算出（物理像素上限 + 工作分辨率）。
  **目前 renderSize 恒等于 captureSize ⇒ 输出尺寸 = 源窗口尺寸。**
- 覆盖层 frame = `appkitRect(fromCG: target.frame)`（`main.swift:1843`），
  4Hz 跟随维持这个相等（`followOverlayFrame`）。

⇒ **缺口只有一个**：把「双线性直通」换成「一道真正的放大重建」，
并允许 **输出尺寸 ≠ 采集尺寸**。别的都在。

## 3. ⚠️ 架构分岔：放大到满屏 ≠ 键鼠还能用（必须拍板）

我们的覆盖层是**点击穿透**的（`ignoresMouseEvents = true`），这是第十三轮定下的唯一输出方式。
它带来一个硬约束：**事件直接落到「指针所在屏幕位置」底下的那个窗口**。

| | 源窗口铺满屏幕 | 720p 小窗口 + 画面放大铺满 |
| --- | --- | --- |
| 覆盖层与源窗口 | 完全重合 | 位置错开 |
| 你看到的 | 放大/重建后的画面 | 放大/重建后的画面 |
| 你点到的 | **就是源窗口** | **画面底下那个窗口**（可能是桌面、别的 App） |
| 结论 | 可以，零风险 | **不行** |

LS 靠「限制游标 / 缩放游标 / 调整游标速度」这一套来处理（它自己接管了光标），
**而「接管输入」正是我们第十三轮故意删掉的那类东西**。

### 三个可选档（推荐 1 → 3a → 2，不建议 3b）

**档 1 · 只加「放大重建」（零输入风险，建议先做）**
源窗口**已经**铺满屏幕（用户自己最大化，或 App 本来就全屏）时，采集到的画面是被源 App
自己（或驱动）双线性放大过的，我们在覆盖层上加一道重建/锐化把清晰度拉回来。
= LS 那个 FSR 档的真实作用。输入、跟随、穿透**一律不动**。
适用：720p 视频/游戏跑在全屏窗口、老游戏、模拟器。

**档 3a · 观影档：画面放大铺满，但明确「不可点击」（零风险）**
窗口不动，画面放大铺满整屏，覆盖层**仍然穿透**。纯看视频/动漫可用（不看点击）。
需要在 UI 上说清「这一档鼠标点击仍落在原窗口位置」。**改动很小**，且没有权限门槛。

**档 2 · 自动把源窗口拉到目标尺寸（要新权限）**
这样「720p 小窗口 → 满屏」才真正成立，而且**输入映射天然正确**（窗口本身就变大铺满了）。
代价：改别的 App 的窗口尺寸**只能走辅助功能（AX）**，本工具目前刻意不依赖这个权限
（Carbon 热键就是为了避开它）；且部分 App 不接受外部改尺寸 / 改完会重排重渲染。
**要不要吃这个权限，得用户定。**

**档 3b · 画面放大铺满 + 自己接管输入（不建议）**
要把屏幕坐标按比例映射回源窗口坐标、合成 CGEvent 送进去，还要兜光标显隐/边界/焦点一堆状态。
这就是被删掉的那个模式。**除非用户明确要，否则不做。**

## 4. 四个候选算法（替换掉那道双线性）

| 候选 | 依赖 / 许可 | 难度 | 定位 |
| --- | --- | --- | --- |
| **CAS**（AMD 对比度自适应锐化） | 自写，~30 行 Metal，MIT | 最低 | 纯锐化。**先用它把管线打通** |
| **MetalFX Spatial**（`MTLFXSpatialScaler`） | **macOS 13+ 系统自带，零第三方** | 低 | 苹果版「FSR」。**建议做默认档** |
| **AMD FSR 1.0 移植**（EASU + RCAS） | 开源，但要手写 Metal 版 | 中 | 用户点名要的「FSR 那种」；与 MetalFX 定位重叠，**二选一** |
| **Anime4K**（`bloc97/Anime4K`） | 原项目 MIT；有 Metal 移植 `imxieyi/Anime4KMetal`（Apache-2.0，GLSL→Metal 运行时翻译） | 最高 | 动漫/线稿/字幕。**用户点名要的 anime4k** |

关于 **MetalFX Spatial** 的实证（Apple 文档 + WWDC2022 "Boost performance with MetalFX Upscaling"）：
- 只要**一张颜色纹理**输入（不需要运动向量/深度）⇒ 正好套我们的采集输出。
- WWDC 的示例参数**就是 1280×720 → 2560×1440**（跟用户举的例子一模一样）。
- 用法：建 `MTLFXSpatialScalerDescriptor`（贵，只在启动/尺寸变化时建一次）→ 每帧
  `scaler.colorTexture = 采到的低清纹理`、`scaler.outputTexture = drawable`、`encode(commandBuffer:)`。
- `colorProcessingMode` 用 `.perceptual`（我们全链路是 sRGB 8-bit，见第十轮结论）。
- ⚠️ **软肋**：苹果明确要求输入**已抗锯齿、无噪点**。游戏 720p 输出带锯齿 ⇒ 会被一起放大。
  这与 FSR 1.0 的固有毛病相同（LS 用户也得靠锐化强度去压）。Anime4K 因为有专门的
  「去锯齿/去糊」前置 shader（`Restore_CNN` / `Deblur_DoG`）反而更适合这类源。

## 5. 代价评估（用我们自己的实测数字，不是猜）

**① 放大本身**：MetalFX / CAS 都是为「比直接渲染高分辨率更便宜」而设计的，
720p→1440p 的开销远小于渲染 1440p。不构成瓶颈。

**② 真正要留意的是下游的 LSFG**：引擎日志里那行
`Metal presentation 380x260 …, multiplier 2, display 144 Hz` 说明
**LSFG 的光流跑在覆盖层的 drawable 尺寸上**。输出尺寸从 720p 提到 1440p，
光流计算量按像素数涨（约 4×）。

好消息是**这个量级我们量过**（第二轮功耗表）：

| 配置（3× / 60Hz，纯 GPU） | GPU |
| --- | --- |
| 2558×1664 + 光流 1.0 | **3.12 W** |
| 2940×1912 + 光流 1.0 | 5.09 W |
| 2558×1664 + 光流 0.5 | 1.03 W |

⇒ **全屏 1440p 上跑 LSFG 大约 3 W GPU**，M4 扛得住。真嫌贵，
`LSFGM_FLOW_SCALE` 是现成的**平方杠杆**（1.0→0.5 直接把光流砍到 1/3 左右）。

**③ 生成帧占比会变**：放大 `generated/total` 不会变（还是 50%/66.6%…），
但**生成帧的绝对像素数变大** ⇒ 插帧伪影会更容易被看见（第十二轮那条结论的推论）。
⇒ 放大档下建议配合降倍率。

**④ 比例与留边**：16:9 窗口 → 16:9 屏幕是干净的 2×；非 16:9 的源必须决定
**拉满（变形）/ 保持比例留黑边 / 整数倍**。LS 有「缩放模式：自动 / 自定义」对应这件事。
我们最小版本可以先只支持「保持比例 + 居中留边」。

**⑤ Retina / 物理像素**：输出尺寸必须按**物理像素**算（沿用 `CGDisplayCopyAllDisplayModes`
那套上限逻辑，铁律第 4 条），本机主屏是 2560×1440 且 `backingScaleFactor = 1`，暂时不踩坑。

## 6. 建议的最小落地路径

1. **第一步（建议直接做）**：把 `present()` 里那道双线性换成 **CAS 锐化**，
   并把 `renderSize` 与 `captureSize` 解耦（新增「输出尺寸」概念，先只做「跟随源窗口」）。
   目标不是画质，而是**把「输出尺寸 ≠ 采集尺寸」这条管线打通并验证**。
   验收：`--dump-output` 出图尺寸 = 目标尺寸；引擎日志 `Metal presentation` 显示新尺寸；
   4Hz 跟随/穿透/延迟测量全部回归通过。
2. **第二步**：把 CAS 换成 **MetalFX Spatial**（默认「FSR 档」），保留 CAS 作为轻量档。
3. **第三步（可选）**：加 **Anime4K** 档（用户点名的 anime4k）。
4. **并行决定**：要不要 档 3a（观影铺满）/ 档 2（AX 改窗口尺寸，需新权限）。

UI 上缩放与插帧**保持两个独立开关**（学 LS）。

## 7. 未验证 / 风险（诚实清单）

- **LS 具体怎么处理输入映射，我没有实测**（无 Windows 环境）。上面「LS 靠限制/缩放游标
  自己接管光标」是从它的官方选项文案推断的，**不是实测结论**。
- **MetalFX Spatial 的实际画质**在「游戏 720p 带锯齿输出」上到底比 CAS 好多少，**没量过**。
  要与 CAS 做一次 A/B 截图对比再定默认档（复用第十二轮那套「质心间距测尺度 + 笔画梯度测锐度」
  的方法，别靠肉眼）。
- **AX 改窗口尺寸**在本机所有目标 App 上的接受度未知，且会引入新权限弹窗。
- **Anime4K 的 Metal 移植**是播放器 App 不是库，复用其 GLSL→Metal 转换器的可行性未评估；
  已知它自己文档里写着「Metal 双线性采样导致输出与原始画面非亚像素对齐」的坑。
- LSFG 在 1440p 上的真实帧率**是否达产**（`generated` 有没有掉）要实测，不能只看功耗。
