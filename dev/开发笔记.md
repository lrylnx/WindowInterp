# 开发笔记（窗口插帧助手）

> 这份文件是 README 拆出来的**开发侧**内容：改道历史、源码结构、自检钩子、测量工具、
> 实测记录。README 只讲功能，过程放这里。

## 改道记录：这条路为什么不能想当然

### 第一版（BrowserInterp）：整屏捕获 + 悬浮层（失败）

| 做法 | 死结 |
| --- | --- |
| 整屏捕获再裁剪到目标窗口 | 源窗口必须一直在屏幕上、坐标一变就错位，还可能把自己的悬浮层一起拍进去（自我镜像） |
| 悬浮层盖在源窗口上 | macOS 判定源窗口「被完全遮挡」，浏览器把视频渲染节流到 ~1fps（黑屏/卡成幻灯片） |

### 第二版：抓窗口 + 独立全屏空间（看着优雅，遇到 Chrome 就死）

抓窗口这半是对的（`SCContentFilter(desktopIndependentWindow:)`，窗口在别的桌面空间也能抓到）。
错的是输出端：把插帧画面输出到**另一个原生全屏 Space**。

看着很优雅（源窗口没被遮挡、四指滑动切空间），但 2026-10-12 被实测推翻：

- 输出窗口一进独立 Space，源窗口就被 WindowServer 标记成 `CGWindowIsOnscreen=false`；
- 源窗口不在当前 Space 时，**系统会冻结它的内容** —— 采集端从第 ~42 帧起再也拿不到
  `complete` 帧，只剩 `.idle`（"这一拍没有新内容"）；
- 现象就是用户报的：**开头 1~2 秒有画面，之后冻住/黑屏**。

关键证据（`~/Library/Logs/WindowInterp/app.log`）：

```
start: ok target=2559 Google Chrome ...
capture: 渲染=25/s (累计 42) luma=69.7 帧状态[complete=42 idle=6]   源窗口[onscreen=false]
capture: 渲染=0/s  (累计 42) luma=69.7 帧状态[complete=42 idle=35]  源窗口[onscreen=false]
capture: 渲染=0/s  (累计 42) luma=69.7 帧状态[complete=42 idle=64]  源窗口[onscreen=false]
```

`luma` 冻在 69.7 就是"画面停在最后一帧"的量化证据（每帧采样 40×40 个点算平均亮度）。

⚠️ **这跟 Chrome 的"省内存模式/节能模式"无关** —— 是 Space 隔离 + 遮挡判定，系统级行为。

### 第三版：贴住源窗口的穿透覆盖层 —— 源窗口一个字都不动

要成立得同时满足三条，缺任何一条都会变成用户看到的那种「没插帧 / 卡住 / 满屏网页元素」：

| # | 条件 | 不满足时的现象 |
| --- | --- | --- |
| ① | **当前 Space 必须是源窗口所在的 Space** | 源窗口内容被 WindowServer 冻结（采集端只剩 `.idle` 帧）⇒ 画面卡住；覆盖层还落在别的空间，用户根本看不到 |
| ② | 覆盖层 `isOpaque=false` **且** `alphaValue<1`，且经 8-bit 量化后 <255（`0.999`→254 ✅；`0.9999`→255 ❌ 实测失效） | 覆盖层把源窗口完全遮住 ⇒ Chrome 判定「被完全遮挡」而停渲染 ⇒ 同样卡住 |
| ③ | 覆盖层必须**精确贴住**源窗口的 frame | 贴合偏了会露出源窗口的边、或盖到别的窗口上。源窗口拖动/缩放后由 4Hz 的 `followOverlayFrame()` 实时跟回来 |

透光率 0.1%，肉眼不可见；LSFG 引擎不受影响（engine 日志 `generated` 正常）。

> ⚠️ 上一版曾用「把源窗口请出原生全屏 + 再铺满屏幕」来绕开 ①。**那是错误方向，已删除**：
> 请出全屏 = Chrome 立刻露出地址栏、书签、网页元素、弹幕、评论，等于「窗口化插帧」——
> 而用户要的正是**满屏只剩视频**。

#### ① 这一步曾经整条失效，原因值得记住

旧代码用 `CGSGetWindowWorkspace` 拿「源窗口在哪个 Space」。这个函数对**原生全屏**窗口
**稳定返回 0**，于是切 Space 静默失败、覆盖层留在桌面空间。用户看到的现象就是：
Chrome 全屏界面里没有插帧画面；切回桌面那块插帧窗口又是卡住的。

改用 `CGSCopySpacesForWindows` 之后一次就对（`源Space=[347] 类型=[4]`、`切换 rc=0`）。
附带：`CGSAddWindowsToSpaces`（把窗口显式搬进某个 Space）在原生全屏 Space 上实测**恒返回
`kCGErrorFailure(1)`**，所以它只当切 Space 失败时的兜底，不当主路径。

## 源码结构

单文件 `main.swift`：

| 部分 | 说明 |
| --- | --- |
| 顶部 | re-exec 注入：`DYLD_INSERT_LIBRARIES=liblsfg_metal.dylib` + `LSFGM_*` 环境变量 |
| `CaptureTarget` / 枚举 | `SCShareableContent.excludingDesktopWindows(false, onScreenWindowsOnly: false)` 拿**全部**窗口（含其他空间），过滤系统窗口和小于 320×240 的 |
| `CapturePipeline` | SCStream 采集 → 最新帧队列（只留最新，丢旧帧）→ **专用串行队列**上 `CIImage` → `CAMetalLayer.present`。渲染必须离开主线程：LSFG 靠**阻塞 present 调用线程**做 vsync 定速，主线程序列化会被堵成成秒的卡顿 |
| `ReconstructMode` / `CASPass` | 输出重建档（`off` / `lanczos` / `cas`）。`CASPass` 现场编译 Metal shader（`device.makeLibrary(source:)`）、建 render pipeline + sampler、按需分配并**复用**两张中间纹理、画一个全屏三角形；编译或建纹理失败会 `disabledReason` 降级回 `lanczos` 并且**只喊一次**（不静默、不每帧刷日志）。`CapturePipeline.present()` 是「重采样 → 翻转 → 写 drawable」三段式，输出尺寸以 **drawable 纹理真实尺寸**为准（唯一真相） |
| `InterpWindow` / HUD | 贴住源窗口的**穿透覆盖层** + 角标 + 独立控制小窗（`gameHUD`，命名是历史遗留，现在是通用小窗） |
| 菜单栏 / 控制窗 | NSStatusItem（主入口）+ NSTableView 窗口列表 |
| `Watchdog` | 主线程看门狗：卡住 5 秒自动 `sample` 抓栈，卡死 30 秒强制退出 |

另有几条铁律写在代码注释里，都是踩出来的：

1. **绝不能给这个 `CAMetalLayer` 设 `presentsWithTransaction`** —— drawable 会押到 CA commit，
   3 个 drawable 池耗尽后 LSFG 的 present hook 被静默旁路（引擎 `generated=0`）。
2. **绝不在 `NSScrollView` 里塞 `NSStackView` 再互相约束宽度** —— AppKit 布局死循环，
   主线程永久卡死（本项目真的卡过一次，靠看门狗抓栈定位）。窗口列表已改用 `NSTableView`。
3. **抓整屏时必须排除本进程自己的窗口**，否则输出窗口拍到自己的输出，无限镜像。
4. **采集/渲染尺寸必须封顶到显示器的物理像素**（`CGDisplayCopyAllDisplayModes` 里渲染像素
   尺寸的最大值），不能拿 `backingScaleFactor` 去乘逻辑尺寸 —— 缩放模式下后者仍返回 2，
   会算出比屏幕还大的工作区，白白烧掉成倍的 GPU。
5. **不要在 `relaunch()` 里传「已经写进 UserDefaults 的设置」** —— 命令行参数优先于
   `UserDefaults`，而传过去的全局常量是**启动那一刻**的旧值，会让用户改完设置后
   新进程又读回旧值（光流设置就这么「改了没用」过一次）。持久化设置只留
   `UserDefaults` 一个真相。
6. **`CAMetalLayer.maximumDrawableCount` 只能是 2 或 3**，设 4 以上 `nextDrawable()`
   永远拿不到，画面一帧都不出。而 2 和 3 对延迟没有可测差别。
7. **输出方式只有一种（贴住源窗口的穿透覆盖层），不要再加第二种。** 那个「铺满整屏 +
   抢 key」的模式是**一整条并行的代码路径**：抢 key 之后要给 Esc/空格/HUD/右键菜单各自兜底，
   还要跟源 App 抢光标显隐，跟随逻辑也得写两套。它在「整屏源」上还和贴源覆盖层**完全等价**
   —— 收益为零、维护成本翻倍。如果将来真需要全屏语义，改**这一条路径**，别再分支。
8. **加滤镜（CAS）的三条硬约束，全是实测撞出来的**（`CASPass` 段注释里有全文）：
   ① 同一张纹理**不能既当输入又当输出**（读写冲突）⇒ 必须先落到中间纹理；
   ② `CAMetalLayer` 的 drawable **没有 `.shaderWrite`**（只有 `.shaderRead` + `.renderTarget`）
   ⇒ 滤镜只能是**片元**（写 renderTarget），不能是 compute；
   ③ **最后一步写 drawable 的必须仍是 Core Image，不能是滤镜 pass 本身** ——
   引擎那边的呈现行为才与「关闭」档完全一致（多翻/少翻一次 = 整幅画倒过来）。
   另外：**uv 的 y 取向只能靠实测定**（`(1.0 - pos.y) * 0.5`），而且推错时会被别的翻转
   **部分抵消**、截图上看着还挺正常 —— 唯一的守门判据是「强度 0 必须与基准档逐像素一致」。
9. **引擎在呈现时会把 drawable 上下翻一次**，所以 `present()` 里那次翻转是拿来**抵消**它的
   ⇒ 要不要翻**取决于引擎在不在**：`displayFlip = offMode ? invertVertical : !invertVertical`。
   写成固定值的话 `--off` 原帧模式会长期上下颠倒。

## 自检钩子（开发用）

```sh
# 列出所有可采集窗口
./窗口插帧助手.app/Contents/MacOS/WindowInterp --list-windows --off

# 不抢焦点、不进全屏，抓指定窗口并把画面存成 PNG（用于判定方向/镜像）
./窗口插帧助手.app/Contents/MacOS/WindowInterp \
    --window-id <ID> --autostart --test-window --test-seconds 15 \
    --dump-output /tmp/wi

# 真实全屏路径（--native-fullscreen，开发用的逃逸舱：输出窗走原生全屏而不是贴源覆盖层）
./窗口插帧助手.app/Contents/MacOS/WindowInterp --window-id <ID> --autostart --native-fullscreen --test-seconds 20

# 复现「源窗口在独立全屏 Space」这个场景（浏览器全屏视频等价物）：
# 不碰用户自己的 Chrome，用一个合成测试源走真正的原生全屏
swiftc -O dev/testpattern.swift -o /tmp/testpattern-native -framework AppKit
/tmp/testpattern-native --native-fs --width 1470 --height 956 --seconds 90 &

# 顺带验「暂停/继续」这条路径：N 秒时暂停、N+4 秒继续
./窗口插帧助手.app/Contents/MacOS/WindowInterp --window-id <ID> --autostart \
    --test-pause 12 --test-seconds 22
```

覆盖层相关的排障开关：`--no-space-switch`（不自动切 Space，用来对比）、
`--solid`（覆盖层不透明，用来验证遮挡判定）、`--overlay-alpha <值>`。
日志里这几行是判据：`output: 覆盖层 … 源Space=[…]`、`space: 切换 … rc=…`、
`output: 切到源 Space switched=…`、`output: 1.5s 后 isKey=… appActive=…`。

`--dump-output` 会写出两张图：`-raw.png`（采集到的原始 CIImage）和
`-window.png`（输出窗口的实际合成结果），配合 `screencapture -l <源窗口ID>` 三方对比，
就能客观判断画面方向对不对。`--dump-control <前缀>` 同理，截的是**控制窗自己**
（用来证明新加的控件真的搭起来了 —— 「编译过了」不等于「功能在跑」）。

输出重建相关的开关：

```sh
# 三档：off（默认，双线性直通）/ lanczos / cas；强度 0…1，0 = 恒等（自检用）
--reconstruct cas --reconstruct-sharp 0.5
# 把输出尺寸解耦到「面板物理像素」（造出「输出 ≠ 采集尺寸」这个确定性场景）
--output-scale fill
# 诊断：只走「CI → 中间纹理 → CI → drawable」，完全不碰 CAS shader
# （用来把「多一个 pass / 多一张中间纹理」的影响和「shader 本身」分开）
--reconstruct-thru-mid
```

两件事不设就会让判据失真（`dev/rec-run.sh` 已经代劳）：

1. **测试窗要开成「内容区 = 渲染尺寸」**。`--test-window` 默认 900×560，而窗口是 `.titled`、
   帧比内容大 **12pt 宽 28pt 高** —— 不补这两个偏移，`CAMetalLayer` 会把纹理再拉伸一次。
   例：源 760×480 ⇒ `--test-w 772 --test-h 508`。
2. **要关掉界面徽标**：`-showBadge NO`（走 `NSUserDefaults` 的参数域）。徽标上有
   `56fps / 57fps` 这种每次都变的数字，会把恒等判据从 100.00% 打到 99.83%
   （差异像素正好是徽标那 247 个 —— 用「差异像素包围盒」一查就现形）。

量延迟（源窗口与输出窗口要同时在同一张截图里）：

```sh
# 1) 起标尺测试源（小窗、放右上角，别被输出窗口挡住）
./dev/testpattern --ruler --width 460 --height 380 --x 980 --y 470
# 2) 起插帧（--test-window 的输出窗固定在左下 60,80 900x560，正好不重叠；
#    --test-x/--test-y/--test-w/--test-h 可自定位置；--test-window 会**强制绕开贴源覆盖层**、
#    改用一个普通小窗，否则输出层会精确贴住源窗口、两个窗口重合 ⇒ 相对位置法恒测出 0 ms）
./窗口插帧助手.app/Contents/MacOS/WindowInterp \
    --window-id <源窗口ID> --autostart --multiplier 3 --test-window --test-seconds 20
# 3) 趁窗口还活着赶紧截图（窗口一关就查不到位置了）
for i in 1 2 3; do screencapture -x -o /tmp/lat-$i.png; sleep 0.3; done
# 4) 分析（输出窗口 ID 来自上面那行 INTERP_WINDOW_ID=）
./dev/latency-probe <源ID> <输出窗口ID> 2.0 /tmp/lat-1.png /tmp/lat-2.png /tmp/lat-3.png
```

⚠️ 每轮必须同时核对引擎日志（`~/Library/Logs/WindowInterp/engine-*.log`）里的
`generated` 是否在涨 —— 否则会把「插帧失效」误读成「延迟很低」。

⚠️ `open -n -a <app> --args ...` 在本机**传不进参数**（args 会是空的），自检要走直启二进制。

### 延迟与功耗的测量工具（`dev/`）

| 工具 | 用途 |
| --- | --- |
| `dev/gpu-energy.swift` | **打印 GPU / CPU / ANE / DRAM 的实时功耗（瓦）**。读 IOKit 的 `IOReport`（`Energy Model` 组），不需要 root —— 就是 `powermetrics` 背后的同一份数据。加 `GPU_ENERGY_VERBOSE=1` 打印各通道原始值 |
| `dev/latency-probe.swift` | **端到端延迟测量**：配合 `testpattern --ruler` 使用，输入窗口 ID + 若干张全屏截图，打印每张的延迟与中位数。`--display <CGDirectDisplayID>` 支持非主屏。原理见「延迟」章节 |
| `dev/lat-round.sh` | **一键跑完一轮延迟测量**（起标尺源 → 起插帧 → 截 14 张图 → 出中位数 + 引擎状态核对）。第 11 个参数起是**额外引擎环境变量**，用来做旋钮 A/B：`dev/lat-round.sh 1 2 2 40 300 700 300 2560 1440 lat1 LSFGM_LATENCY=1`。整轮输出同时落到 `/tmp/lat-round-<标签>.out`。注意 `screencapture -D` 吃的是**在线屏枚举序号**（实测 1=主屏、2=内建），不是 CGDirectDisplayID |
| `dev/displays.swift` | 列出在线显示器：CGDirectDisplayID / 全局 bounds / 刷新率 / 是否主屏内建屏 |
| `dev/clickreceiver.swift` + `dev/clicktest.swift` | **输入穿透验证**：接收窗把每次 mouseDown 打到 stdout；clicktest 往 HID 层合成一次真实点击（CG 全局坐标）。覆盖层盖住接收窗后点它正中，事件仍能到达即穿透成立 |
| `dev/testpattern.swift` | 动态测试源：内容确定、每帧都在变的窗口（Core Animation 驱动，本进程 CPU ≈ 0），用来做可复现的功耗 A/B。`--ruler` 切换成延迟标尺画面（红/蓝定标 + 匀速白扫描条），`--static` 切换成**整幅画面完全不动**，`--move-demo [秒]` 让**源自己周期性移动/缩放**（用来验覆盖层跟随），`--x/--y` 指定窗口位置。`--soft` 换成**低分辨率源**（半分辨率位图里画细字/细线/中对比灰块，整张用 `.linear` 放大）—— 输出重建的判据必须用它：现有动画图案全是**硬边**，而 CAS 的设计恰恰是「强边缘处自动不锐化」，拿硬边图案量 CAS 等于量了个零。注意它必须用 **normal 层级**（`windowLayer == 0`）—— 用 `.floating`（层级 3）会被采集侧的 `windowLayer == 0` 过滤条件排除掉 |
| `dev/probe-frames.swift` | **只查一个窗口的 frame，按固定频率打印**（`probe-frames <windowID> <秒数> <频率Hz>`），同时把 `SCShareableContent` 夹在两次 `CGWindowListCopyWindowInfo` 之间做对照。⚠️ **本工具第一版自己有测量伪影**：`SCK` 全量枚举实测 **39–43 ms**，比 50 ms 的采样间隔还长，先 CG 后 SCK 就变成拿 `CG(t)` 比 `SCK(t+40ms)`，源这时正在移动 ⇒ 打印出假的「不一致」。所以现在是 `CG1 → SCK → CG2`，`CG1 != CG2` 就判「移动中，本拍对比无效」 |
| `dev/measure-gpu.sh` | 采样 GPU 利用率（`ioreg` 的 `Device Utilization %`） |
| `dev/measure-power.py` | 用电池放电电流 × 电压估整机功耗 |
| `dev/list-modes.swift` | 列出显示器的全部显示模式（点尺寸 / 渲染像素 / 刷新率） |
| `dev/rebuild-lsfg-dll.py` | **把别的 PE 里的 LSFG 着色器重灌进 `lsfg-vk.dll`**（换核工具）。`--probe <pe>` 打印某 PE 的资源段全貌；`--minimal <骨架PE> <新着色器来源PE> <输出/lsfg-vk.dll>` 走**最小改**路线（资源目录树一字节不动，只重写数据块并更新 DataEntry）—— 从零重建整棵树会被引擎的严格校验拒掉 |
| `dev/engine-probe.sh` | **配置体检**（不量端到端延迟，只收引擎统计）：`dev/engine-probe.sh <标签> <倍率\|off> <工作分辨率\|0> <光流> <源宽> <源高> [额外 KEY=VALUE ...]`。跑 16 s 后打印 `generated` 达产情况、`enqueue_display` 延迟分解、`display intervals` 的 `late`。整轮输出落盘 `/tmp/probe-<标签>.out` |
| `dev/rec-run.sh` | **输出重建档的跑批**：同一份 `--soft` 源跑 `off` / `cas0` / `cas` / `lanczos` 四档，每档落两张 PNG。`./dev/rec-run.sh <目录> [额外参数…]`，额外参数原样透传。⚠️ 它会自动把测试窗开成 **内容区 = 源尺寸**、并 `-showBadge NO` |
| `dev/cmp-reconstruct.py` | **输出重建的客观判据**：平均亮度 / 平均绝对梯度 / 高频能量 / 暗度加权质心，外加**恒等判据**（CAS 强度 0 必须与基准档逐像素一致）。`--ab <off> <cas0> <cas> <lanczos>` 一次出四档对照表；不给 `--crop` 时自动裁掉窗口边框并内缩 12px |
| `dev/orient-run.sh` | **朝向判定**（正立 / 上下颠倒 / 左右镜像）：对同一张 `--soft` 源逐个配置截**屏幕上的真实窗口**，自动裁掉窗口阴影/边框后比「行剖面 vs 源」与「列剖面 vs 源」 |
| `dev/verify-perfmode.sh` | **「性能模式」开关的判据**：把偏好写成 true / false 各跑一轮引擎探测，断言**引擎回声里的 `Performance mode` 等于写的那个值**（能区分 A/B），并断言同一轮里 `generated` 还在涨 —— 一个开关「没生效」是静默的，而插帧「失效」会伪装成省电成功。跑完原样还原用户的偏好（`defaults read` 把布尔读成 1/0，`-bool 1` 是非法的，要归一化，否则还原会静默失败） |

⚠️ 关于测量方法本身，两个必须记住的坑：

1. **`Device Utilization %` 不是功耗。** 它实际是「GPU 有工作在跑的时间占比」：分辨率降了
   44%，它照样稳定显示 94%。判断省了多少电**只能**以 `dev/gpu-energy` 为准。
2. **电池电流法噪声太大。** Apple 电池计的 `InstantAmperage` 更新很慢，同一个负载两次读数
   能差一倍，只适合看量级，不能用于结论。
3. 跑测量时**启动的进程不能跨命令块存活**（`nohup ... & disown` 也留不住），整轮测量
   必须写在同一条命令里。

## 延迟：试过、但没用的旋钮（都实测过，别重复踩）

| 尝试 | 结果 |
| --- | --- |
| `--no-auto-fps --capture-fps 60`（放开采集上限） | 无效。引擎日志里 `source_fps` 仍稳在「屏幕刷新率 ÷ 倍率」 |
| `--drawable-count 2` | 无效（186 ms vs 184 ms）。而且 `maximumDrawableCount` **只能设 2 或 3** |
| `--no-display-sync`（不等垂直同步） | 无效（186 ms vs 184 ms），只牺牲画面整齐度 |
| `LSFGM_TARGET_FPS=120` | 无效，甚至略差（196 ms） |
| `--queue-depth 2` | 唯一有效但很小：约 −20 ms |
| `--queue-depth 1` | **更糟**：SCK 大面积丢帧，画面一顿一顿 |
| `--resolution 1080`（降低采集分辨率） | 无效（196 ms）。省 GPU 但不省延迟 |

### 引擎级旋钮（`--engine-env`，不用改代码就能试）

启动时用 `--engine-env KEY=VALUE` 覆盖（可重复多次）：

```sh
./窗口插帧助手.app/Contents/MacOS/WindowInterp --engine-env "LSFGM_FLOW_SCALE=0.75"
```

**全量实测结论：这 6 个旋钮对延迟全部无效**（落在 ±1 ms 噪声内），其中两个曾记作**掉产**
（其中一个已被第十六轮的重测推翻，见下）。延迟 99% 花在「等 vblank 上屏」，没有旋钮能碰。

> ⚠️ 更新（第十六轮）：`LSFGM_PERFORMANCE_MODE` 那条「掉产」被重测推翻了 —— 3× / 1920×1080 下
> 开与不开的 `generated` 完全相同（958 = 958）。**它是这一堆旋钮里唯一一个值得做成 UI 的**，
> 但理由不是延迟也不是产率，而是**功耗**（见第十六轮）。

| 变量 | 作用 | 实测结论 |
| --- | --- | --- |
| `LSFGM_FLOW_SCALE` | 光流工作分辨率缩放，`0.25`–`1.0` 或 `auto` | **唯一值得动的画质旋钮**。对延迟几乎无影响，代价在功耗（算力随它平方变化）。默认 `1.0` |
| `LSFGM_PERFORMANCE_MODE` | 换轻量着色器组（= 小黄鸭 LSFG 3.1 的 Performance mode） | 延迟无变化（延迟由倍率/刷新率定，旋钮碰不到）。**它省的是电不是延迟**：第十六轮重测 GPU **3.40 W → 0.99 W**，且 `generated` 一张不少（958 = 958）⇒ 已做成 UI 开关。⚠️ 本行原先记的「生成帧掉 4.6%」按第十六轮数据不成立，见那节 |
| `LSFGM_PACING_MODE` | 节奏模式（默认 `vsync`） | 延迟无变化。`adaptive` 也**不再让插帧失效**（`generated` 正常增长），但也没降延迟 |
| `LSFGM_OVERRIDE_PRESENT_MODE` | 覆盖 present mode | ❌ 延迟无变化 |
| `LSFGM_PRESERVE_SWAPCHAIN_IMAGE_COUNT` | 保留交换链影像数 | ❌ 延迟无变化 |
| `LSFGM_LATENCY` | **引擎自带延迟统计** | ⚠️ **只报数，不降延迟**。**但是目前唯一能看见帧节奏的工具** |
| `LSFGM_TARGET_FPS` | 输出帧率上限 | 已默认 = 屏幕刷新率 |
| `LSFGM_NO_FP16` | 关半精度 | ❌ 延迟无变化，**生成帧掉 6.6%** |

也可以用配置文件：`/etc/lsfg-metal/conf.toml`、`~/.config/lsfg-metal/conf.toml`
（`LSFGM_CONFIG` 可指定路径）。本机两份都不存在（从没启用），但它支持按 App 分档
（`profiles` / `kind` / `executable name` / `Steam App ID` / 兜底）—— 可以做到
「视频 App 用 5×、游戏用 3×、其他用 2×」自动切换。

### ✋ 一个必须记住的陷阱：`generated=0` 会伪装成「延迟很低」

`LSFGM_PACING_MODE=adaptive` 那一组测出来只有 **18 ms**，看着像神优化 ——
实际是引擎**根本没在生成帧**：日志里 `generated=0`、`total` 恰好等于 `source`。
它**不报任何错误**，延迟自然就只剩采集+显示那 20 ms。

⇒ **任何延迟测量都必须同时核对引擎日志的 `generated` 是否在涨**，
否则会把「插帧失效」当成「优化成功」。

### 延迟到底花在哪（引擎自报分解）

开 `LSFGM_LATENCY=1` 后引擎会把内部延迟拆开写进日志（`--engine-env` 运行时给）：

```
Metal display intervals=240 p50_ms=6.945 p95_ms=13.889 stdev_ms=3.1 late=60
Metal latency kind=original  samples=120 dropped=0 enqueue_display_ms=26.2/30.0 \
      queue_ms=0.012/0.029 worker_ms=0.35/0.88 drawable_ms=0.011/0.044 submit_display_ms=25.9/29.3
Metal latency kind=generated samples=120 dropped=0 enqueue_display_ms=19.4/23.2 \
      queue_ms=0.012/0.026 worker_ms=0.30/0.58 drawable_ms=0.026/0.045 submit_display_ms=19.2/22.7
```

（每项是 `p50/p95`，单位 ms；144Hz 下一个刷新周期 = 6.944 ms。）

| 环节 | 实测 | 含义 |
| --- | --- | --- |
| `worker_ms` | **0.35 / 0.30** | 光流 + 插值**计算本身**。400p 下连 1 ms 都不到 |
| `queue_ms` / `drawable_ms` | **0.01** | 排队、取 drawable —— 完全不是瓶颈 |
| `enqueue_display_ms` | **26.2（原帧）/ 19.4（生成帧）** | 入队 → 真正上屏。**99% 的延迟在这里** |
| `display intervals` | p50 = 6.945 = **恰好 1 个刷新周期** | 引擎中位数每个 vblank 送一张新画面（合格）；p95 = 2 个周期、`late` ≈ 25% 说明偶尔漏拍 |

**两条结论**（这也解释了为什么过去所有软件旋钮都无效）：

1. **延迟全在「送显排队」，不在采集、也不在光流计算。** 引擎自报原帧
   `enqueue_display` ≈ 26 ms，标尺法测的端到端也是 26 ms —— 两个独立通道对上了。
   ⇒ 降延迟只能改「一帧要等几个 vblank 才上屏」：**倍率**和**屏幕刷新率**。
2. **`LSFGM_LATENCY=1` 本身不降延迟。** A/B 交错重复各 3 轮、每轮 15 个样本：
   关 = 25 / 26 / 27 ms，开 = 26 / 26 / 29 ms —— 差异落在噪声内（±2 ms）。

### 倍率与「帧节奏」

`Metal display intervals=… late=N` 是**帧间隔超过一个刷新周期的比例**。
它不随任何旋钮变，**只随倍率剧烈变化**：

| 倍率 | 实测源 fps | 输出 fps | `144 ÷ 输出` | `late`/240 | 生成帧延迟 p50/p95 | `worker_ms` p95 |
| --- | --- | --- | --- | --- | --- | --- |
| **2×** | 57 | 114 | **1.26** | **62（26%）** | 20.6–22.2 / 23.4–25.7 | **0.5** |
| **3×** | 46 | 138 | 1.04 | 9（3.8%） | 23.2–24.8 / 29.2–30.1 | 3.0 |
| **5×** | 29 | 145 | **0.99** | **1（0.4%）** | 27.6–32.8 / 39.6–46.5 | **20** |

**规律：`late` 由「刷新率 ÷ 输出帧率」是否接近整数决定**（1.26 ⇒ 26%、1.04 ⇒ 4%、
0.99 ⇒ 0%，三条严丝合缝）。高倍率反而更顺，是因为采集被钳到 `刷新率 ÷ 倍率`，
输出自然贴到刷新率上。代价：① 延迟随倍率升；② **`worker_ms` 长尾暴涨**（2× 的 p95 = 0.5 ms，
5× = **20 ms**）—— 这是「高倍率偶发一顿」的来源。

**两个可直接用的结论：**

* **24 fps 视频别用 5×**：24×5 = 120，144/120 = 1.2 ⇒ 节奏不整。最佳是 2× 或 3×。
* **60 fps 游戏用 3× 而不是 2×**：3× 会把采集钳到 48 ⇒ `late` 从 26% 掉到 3.8%，
  延迟只多 2.6 ms。
* ⚠️ **5× 会把 60 fps 的源砍到 29 fps**（`effectiveCaptureFPS` 的 budget）⇒ 源信息量掉一半
  ⇒ 插出来的帧是低信息帧的插值、动起来迟滞。

### 唯一真正能改善高倍率延迟的办法：换高刷屏

144Hz 主屏上 3× 实测 **28 ms**、4× **35 ms** —— 比 60Hz 屏上的 2×（50 ms）还好。

### 怎么量出来的

`dev/testpattern.swift --ruler` 会画一个只有三样东西的画面：左边缘红色定标、
右边缘蓝色定标、中间一根**匀速平移的白色扫描条**（周期 2 秒）。
把源窗口和插帧输出窗口并排摆开，一次全屏截图里两边的定标和扫描条都在，
比较扫描条在两根定标之间的**相对位置**：

```
延迟 = Δ相对位置 × 扫描条周期
```

为什么用相对位置：输出窗口是 aspect-fit（一定有黑边）、缩放比未知、窗口位置未知 ——
相对位置把这些全部消掉。`dev/latency-probe` 只统计像素在 **x 方向的重心**，
所以连截图里图像是正立还是倒立都不影响。对照验证：**原帧模式测出来 18–20 ms**，
与「采集+渲染+显示」的合理量级一致。

## 实测记录

2026-10-12，Apple M4 / 16GB / macOS 15.8.1 / 内建屏 2560×1664 @60Hz：

- 抓 WorkBuddy 窗口（800×869 点 → 采集 1600×1738）：引擎 `source=420 original=420 generated=417`
  ——**1:1 插帧**；输出窗口截图确认画面方向正确、无镜像。
- 抓「红果短剧」窗口走**真实全屏路径**：`IS_FULLSCREEN=true WINDOW=(0,0,1710,1069)`，
  引擎 `source=600 generated=598`。
  ⚠️ 当时据此写成「在独立全屏空间下源窗口持续出帧 ⇒ 输出到另一个全屏窗口没问题」——
  **这个结论后来被推翻**：当时量的是**视频 App**（自己铺满屏幕的普通窗口，不是原生全屏），
  而 **Chrome 的原生全屏**会进独立 Space，源窗口随即被冻结。
- 整屏抓取（3420×2224，排除自身窗口）：帧正常，无自我镜像。

引擎统计来自 LSFG 自己的日志（`~/Library/Logs/WindowInterp/engine-*.log`），
**没有用外部设备独立测量屏幕实际呈现次数**。端到端延迟是另一条独立通道量的
（`dev/latency-probe` 从全屏截图的画面内容反推，不依赖引擎自报）。

### 第二轮：功耗排查

用户在「更多空间」缩放（逻辑 1710×1069，渲染 3420×2224）下跑 3×，整机功耗 20 W。

**根因**：`NSScreen.backingScaleFactor` 在缩放模式下仍返回 2，所以「逻辑尺寸 × 2」得到
3420×2138，而这块屏的**面板物理分辨率只有 2560×1664**。多出来的 1.72 倍像素，
系统之后会下采样丢掉。

用 `dev/gpu-energy` 逐项量化（3× / 60Hz，纯 GPU 功耗）：

| 配置 | GPU | DRAM |
| --- | --- | --- |
| 基线（仅画面在动） | 0.16 W | 0.12 W |
| 2940×1912 + 光流 1.0（旧行为） | 5.09 / 5.30 W | 0.91 / 0.92 W |
| 2558×1664 + 光流 1.0（新默认） | 3.12 / 3.12 / 3.25 W | 0.72 / 0.73 W |
| 2558×1664 + 光流 0.5 | 1.03 / 0.97 W | 0.45 / 0.46 W |
| 1660×1080 + 光流 1.0 | 1.17 W | 0.38 W |
| 2558×1664 + 2× 而不是 3× | 2.70 W | 0.71 W |

（每组测两到三次，重复性良好。）

两个反直觉的结论：

1. **光流缩放比分辨率更管用**：分辨率降 44% 只让 GPU 从 5.3 W 掉到 3.1 W，
   而光流 1.0 → 0.5 直接掉到 1.0 W。因为光流计算量随分辨率**平方**增长。
2. **倍率的影响没那么大**：3× → 2× 只从 3.12 W 降到 2.70 W，说明开销主要来自
   「每帧光流」而不是「生成多少帧」。

空闲状态（不插帧、控制窗关着）的 GPU 增量 ≈ 0，说明每秒一次的全窗口枚举
确实是纯浪费（已改成按需）。

### 第三轮：光流设置不生效 + 延迟

用户报了两个问题：① 延迟，尤其 2× 以上；② 光流设置选了不生效、永远回到 1.0。

**问题②的真身：命令行参数把偏好设置盖掉了。**

`relaunch()` 里写着 `args += ["--flow-scale", flowScale]`，而这个 `flowScale` 是
**进程启动那一刻**求值的全局常量。用户改设置时新值只写进了 `UserDefaults`，
重启后新进程却先读到命令行里的旧值（`argument()` 优先于 `preferences`）——
于是引擎参数、界面勾选统统回滚到 1.0。

实测证据：`defaults read local.windowinterp` 里 `flowScale = "0.5"`（写进去了），
但引擎日志 41 次 `Flow scale: 1.00`、只有 2 次 `0.50`（那 2 次还是命令行直传的）。

**修法**：`relaunch()` 不再传递任何「已持久化到 UserDefaults」的设置，
让 `UserDefaults` 成为单一真相。顺手给 `--engine-env KEY=VALUE` 加了环境变量透传。

**问题①的量化结果**（`dev/latency-probe`，60Hz 屏）：

| 配置 | 端到端延迟 |
| --- | --- |
| 原帧模式（不插帧，对照） | 20 ms |
| 2× | 50 ms |
| 3× | 185 ms |
| 4× | 285 ms |

把所有能想到的旋钮都试了一遍，**只有 queueDepth 有约 20 ms 的效果**，其余全部无效或有害。
过程中差点被一个假象骗过去：`LSFGM_PACING_MODE=adaptive` 那组只有 **18 ms**，
实际是引擎**根本没出帧**（日志 `generated=0`，且不报任何错）。⇒ 此后所有延迟测量都强制核对 `generated`。

### 第四轮：Chrome 全屏「只有 1~2 秒有画面」

用户报：插帧 Chrome 的全屏视频，只有 1~2 秒有画面，之后黑屏。

**根因不是 Chrome 的省内存/节能模式**，是两件系统行为叠加：

1. 浏览器原生全屏会把窗口放进**独立 Space**，而我们的覆盖层当时进不去；
2. 源窗口不在当前 Space 时，WindowServer **冻结它的内容** ⇒ 采集端只剩 `.idle` 帧。

复现与修复都用「原生全屏的合成测试源」做（`dev/testpattern.swift --native-fs`）：

| 实验 | 结果 |
| --- | --- |
| 同一 Space + 完全不透明覆盖 | 30 帧后停（遮挡判定成立，`.idle` 涨） |
| 同一 Space + `isOpaque=false` + `alpha=0.999` | **30fps 跑满，`complete` 持续增长** ✅ |
| 源在别的 Space（改造前，`CGSGetWindowWorkspace` 取 Space） | 切 Space 静默失败（全屏窗口返回 0）⇒ 用户看不到插帧 |
| 源在别的 Space（改造后，`CGSCopySpacesForWindows`） | `switched=true`，源 `onscreen=true`，30fps 跑满 ✅ |

### 第五轮：输入穿透 + 高刷屏延迟矩阵

**① 输入穿透** —— 跟手的正确解法是**输入路径与画面路径分离**：覆盖层贴住源窗口 +
`ignoresMouseEvents=true`（点击穿透）+ 不激活不抢 key + 系统光标本来就合成在所有窗口之上。
事件转发（`CGEventPostToPid`）是错误路线（目标不在前台就不处理键盘事件）。
验证（`dev/clickreceiver` + `dev/clicktest`）：

```
game: 输入穿透已开启 ignoresMouseEvents=true 覆盖层=(300,400,600,428) 源=(300,612,600,428)
game: 1.5s 后 isKey=false appActive=false ignoresMouseEvents=true 覆盖层=onscreen=true layer=3
CLICK local=300,200 clicks=1          ← 合成点击穿透覆盖层，命中其正下方的接收窗中心
capture: 渲染=47/s (累计 419) 帧状态[complete=419]   ← 被盖住的源持续渲染，无 idle
```

**② 144Hz 高刷屏延迟矩阵**（`dev/lat-round.sh`，源 640×400 / 光流 0.5 / queueDepth 3）：

| 倍率 | 60Hz 主屏 | 144Hz 主屏 | 60Hz 副屏（参考） |
| --- | --- | --- | --- |
| 原帧 | 20 ms | 14 ms | 17 ms |
| 2× | 50 ms | **21 ms** | 117 ms ⚠️ |
| 3× | 185 ms | **28 ms** | 206 ms |
| 4× | 285 ms | **35 ms** | — |

定案：**之前 3× 的 185ms 就是 60Hz 屏导致的**（源被压到 20fps 进饥饿区）；
144Hz 上延迟 =（倍率＋1）个刷新周期，完美线性。另发现 **引擎按主屏刷新率排程** ——
输出在 60Hz 副屏时引擎仍按主屏 144Hz 排程，2× 多吃约 60ms，所以**要插帧的窗口放主屏**。

### 第九轮：`LSFGM_LATENCY=1` 能不能降延迟（结论：不能，但拿到了延迟分解）

A/B 交错重复各 3 轮，每轮 15 个样本（每轮都核对了 `generated` 在涨）：

| 轮次 | `LSFGM_LATENCY` | 中位数 |
| --- | --- | --- |
| base（第一轮） | 关 | 25 ms |
| base-a / base-b | 关 | 27 / 26 ms |
| lat1（第一轮） | **开** | 29 ms |
| lat-a / lat-b | **开** | 26 / 26 ms |

⇒ **在噪声内（±2 ms），`LSFGM_LATENCY=1` 不改变延迟** —— 它是诊断开关。

⚠️ **本轮数字比历史 21 ms（2×）高约 4~5 ms，原因未定** —— 但**不是插帧退化**，
也不是「别人抢 GPU」：连**不插帧**的基线也一起从 14 → 18/19 ms，是一个**与倍率无关的
加法偏移**（`2× − off` 仍是 7~8 ms）⇒ 慢在「采集 → 渲染 → 送显」这条*固定*链路上。

初版这里写的是「因为用户自己还有个 5× 实例在跑、抢 GPU」——**这句是错的**，已被用户
当场纠正，证据站在他那边：那个实例的引擎日志 `engine-55379.log`（按 pid 命名）
最后一笔停在 **19:34**，本轮全部测量发生在 **19:40–19:45** ⇒ 它当时**根本没在出帧**。
**「进程活着」≠「在算帧」**。

⇒ **绝对值的跨会话比较不可靠**；所有结论都建立在**同一次会话内的 A/B** 上。

### 第十一轮：自动倍率（按窗口帧率自适应）

* 判据模型可离线验算：`输出 = min(min(S, R÷倍率) × 倍率, R)`、
  `节奏抖动 ≈ |R/输出 − round(R/输出)|`（与引擎自报 `late` 线性吻合）。
* 实测验证六个场景全绿：主链（2×→3×→定档）、降档链、额度闸门、单调降档、
  静止画面（`testpattern --static`，采集侧 `complete=1 idle=2728` 真不出帧 ⇒
  「样本 0 条 → 保持 2×」）、真实默认路径（量到 69fps → 定档 2×，零重启）。
* **测试抓到并修掉四个「看起来对、实际是错」的问题**：
  ① 撤掉误杀判据 `worker p95 > 2.5 周期`（5× 客观 `late 0.4% / dropped 0 / 输出 145`
  是最好的那档，却被 p95 19.8ms 判死 —— **代理指标不能压过真实结果**）；
  ② 修掉「样本不足时把样本清空」的死循环（症状：日志静默 47 秒、界面像卡死）；
  ③ 修掉「拿被采集上限钳过的观测值 比 没钳的规划值」的同口径错误；
  ④ 修掉降档序不单调（评分序会从 2× 跳到 6×/8×，越降越激进，实测一路爬到 8× 卡住）。

### 第十二轮：查证「插帧后字变糊」（结论：正常，不可再优化）

### 第十四轮：给跟随加垃圾帧守卫 + 收尾

第十三轮留下一个「3 次 CG 与 SCK 不一致」的悬案。这轮把它查穿：

- **结论：那是探针自己的测量伪影，不是系统 API。** 旧探针先调 `CGWindowListCopyWindowInfo`
  再 `await` 一次昂贵的 `SCShareableContent` 枚举，而枚举实测 **39–43 ms**，
  比 50 ms 的采样间隔还长 ⇒ 实际是在拿 `CG(t)` 比 `SCK(t+40ms)`，源窗口这时正在移动。
- **决定性实验**：把 SCK 夹在两次 CG 之间（`CG1 → SCK → CG2`）。结果 **「两边都有值且不同」= 0
  次**（240 拍），而 **「枚举期间源动了」= 7 次**。**两类 API 在稳态下完全一致。**
- 顺带量到：`CGWindowListCopyWindowInfo` 在 `setFrame` 后 **~17 ms** 就刷新了，4Hz 跟随绰绰有余。
- **产品侧的处置**：那次未复现的 `@790,278`（应为 `@790,762`）**仍未定性**，没找到根因、
  也不声称已修。只做了两件**零风险**的事：① 跟随里加「frame 不落在任何屏幕内就跳过这一拍」
  的守卫；② 日志扩成 `CG@x,y AppKit@x,y screen=<屏名> front=<bool>`，复发时留数据。

验证（全部实测）：覆盖层跟随 **12 次移动 + 4 次缩放逐条吻合**，零误伤、零丢帧。

### 第十五轮：输出重建档 1（Lanczos + CAS），顺带修掉「原帧模式上下颠倒」

**做了什么**（见 README「输出重建」章节）：新增 `ReconstructMode`（`off`/`lanczos`/`cas`）
+ `CASPass`（自写 Metal 片元 shader），`present()` 重写成「重采样 → 翻转 → 写 drawable」三段式，
**输出尺寸与采集尺寸解耦**。UI 进控制窗「性能」那一行最后一个下拉 + 菜单栏「输出重建」子菜单，
改档**不用重启**。新增测试源 `testpattern --soft`、三个 dev 工具
（`rec-run.sh` / `cmp-reconstruct.py` / `orient-run.sh`）。

**三条把自己坑了的错，都是"工具静默给假数据"那一类**：

1. **CAS 的 uv 写反 ⇒ 画面上下颠倒**，而并排截图上「看着也挺清楚」。分四步排除才定案：
   采集侧两图 MAE 0.0005（不是探针问题）→ 旧版跑同一测也这样（不是新引入的）→
   加诊断档 `--reconstruct-thru-mid` 实测与 `off` 一致（不是"多一个 pass"）→ 跑 6 格矩阵
   发现**引擎的翻转是一视同仁的**，而 CAS pass 相对 `off` 多翻了一次。修法是 uv 取
   `(1.0 - pos.y) * 0.5`，与「CI 收尾」结构配套。**教训：uv 取向只能靠实测定，不能靠推理。**
2. **`rec-run.sh` 只吃到了第一个额外参数**（`EXTRA=${(z)1:-}` 而不是数组）⇒
   `--resolution 240 --output-scale fill` 后半截被默默丢掉，判据"全绿"其实跑的还是默认档。
   改成 `EXTRA=("$@")`。
3. **判据被两样东西污染**：界面徽标上的 `56fps/57fps`（每次都不一样，247 个像素）和
   `--soft` 源右下角那个 6×6 闪烁红点（它**必须**闪，静态窗口 SCK 不送帧）⇒
   跑批加 `-showBadge NO`，判据自动裁窗口边框并内缩 12px。

**顺带发现的长期 bug**：为了判定 uv 取向才去截「屏幕上的真实窗口」，结果发现
**`--off` 原帧模式的输出一直是上下颠倒的** —— 根因是引擎在 `Metal presentation` hook 里
会翻一次 drawable，而 `present()` 里那次翻转是拿来抵消它的。为什么第一版 `orient-run.sh`
没抓到：判据没裁窗口阴影，每张图最上面都有一条窄暗边，所有配置都被判成「文字在顶 = 正立」，
**零区分度** —— 判据本身错了比没判据更危险。

**验证**：恒等 100.00%；锐化 输出=采集 梯度/高频 **+15.1% / +18.9%**、
放大路径 **+30.5% / +55.8%**；质心位移 < 1（没变形）；放大路径下 Lanczos 相对双线性
**+17.4% / +27.8%**。生产路径（覆盖层 + 引擎 2×）`eng-cas` 截图正立、引擎
`generated=718 / total=1438`（2× 达产）。代价生产路径 **+0.30~0.41 W**。

### 第十六轮：把「性能模式（轻量着色器）」做成开关

**起因**：本机装了 `MetalFrame.app`（同样用 lsfg-metal 内核），它的插帧参数面板上有一项
**「性能模式（轻量着色器）」**；小黄鸭 LSFG 3.1 也加过同名功能（官方口径「GPU 负载最多减半」）。
去查这个开关到底做了什么，发现本工具**早就把它的环境变量接好了**（`main.swift` 里
`if performanceMode { setenv("LSFGM_PERFORMANCE_MODE", "1", 1) }`），但**界面上没有入口** ——
只有命令行 `--performance` 摸得到，所以用户点不着。本轮只是把它接到 UI 上 + 实测它的真实收益。

**机制**（三条独立证据，互相对得上）：

1. `strings liblsfg_metal.dylib` 里有 `LSFGM_PERFORMANCE_MODE`；`MetalFrame` 主程序里
   也是同一串（`"LSFGM_PERFORMANCE_MODE" = "`，启动时注入），另有 `conf.toml` 的
   `performance_mode = true` 写法 ⇒ **它就是引擎的环境变量，不是宿主自己实现的**。
2. 引擎启动回声直接报出来：`(lsfg-metal) [INFO]: Performance mode: true/false`
   ⇒ **有独立通道证明它生效了**，不用猜。
3. 小黄鸭官方文档（FPSHQ 的 LSFG 词条）：Performance mode 是 **LSFG 3.1 加的**，
   「up to 2× less load」，官方建议「GPU 满载时开」。与实测方向一致。

**实测**（M4 / 本机主屏 2560×1440@100Hz / 源 1920×1080 / 3× / 光流 1.0，用
`dev/engine-probe.sh` + `dev/gpu-energy` 同一轮采，各两轮）：

| | GPU 功耗 | `generated`（`source=480` 那一拍） |
| --- | --- | --- |
| 关（默认） | 3.40 / 3.10 W | **958** |
| 开 | 0.99 / 1.03 W | **958** |

⇒ **降到约 1/3，而帧一帧没少。** 原因在第十轮那个结论里：输出被 vblank 定速
（`source_fps=32`，32 × 3 ≈ 100Hz 贴住刷新率），引擎算得快慢**不改变一秒能上屏几张**，
只改变耗多少电。所以这条旋钮的价值**只在功耗侧**，延迟一个字都不动。

⚠️ **红线复检**：功耗降这么多，第一件要查的就是「是不是插帧静默失效了」——
按第十轮那个陷阱（`generated=0` 会伪装成延迟很低），这里逐轮核对了 `generated` 在涨
且两模式数值相同。另外顺手验了 `source_fps`、`late` 都没变。

**接线注意**：

* ⚠️ **不能**像 `--resolution` 那样在 `relaunch()` 里把新值当命令行参数转发 ——
  `--performance` 的优先级比 UserDefaults 高，转发旧值会把用户刚勾的选项按回去
  （`--flow-scale` 就是这么踩的）。唯一真相是 UserDefaults，新进程自己读。
* 默认**关**：它确实拿画质换电（引擎侧语义是「轻量着色器」），不能替老用户改默认行为。
* 顺手记一个**没做**的决定：`LSFGM_OVERRIDE_PRESENT_MODE`（MetalFrame 的「强制接管呈现队列」）
  和 `MTL_HUD_ENABLED`（MetalHUD）引擎都收、不会报 `Unrecognized`，但前者在本工具上
  **量不出任何用户可见效果**（第十轮已记「延迟无变化」），做成开关就是假功能；
  后者是 macOS 自带的诊断浮层、不是性能开关。两个都能用 `--engine-env KEY=VALUE` 直接试，
  所以**没有进 UI**。

**验证**：`dev/verify-perfmode.sh` 4 项全绿（两轮各自的「引擎回声 = 写的偏好」+「`generated` 在涨」）；
控制窗 `--dump-control` 两态截图复选框勾选状态都对；`zsh build.sh` 编译 + 固定身份签名通过。
**未做**：性能模式下的插值**画质**逐像素对照（没有可靠的同相位取样手段 —— 生成帧的相位不可复现，
硬比会拿 `A(t)` 比 `B(t+Δ)`）⇒ README 里只说「画质略有让步」，不编造百分比。

### 第十七轮：能不能用上 FSR4（结论：接不上，改走空间超分）

用户看到网上笔记（`fsr4-native-macos` + CrossOver 容器 → 游戏内开 DLSS 即得 FSR4），
问能不能给本工具提画质。完整评估写进 `FSR4-可行性-2026-10-16.md`，这里只留结论。

**结论：FSR4 接不进我们这条链，而且不是「工程量」问题 —— 是输入契约不满足。**
（先分清：10-12 评估的是 **FSR 1.0 = 空间超分，只要一张颜色图**；FSR4 是**时域超分**，另一码事。）

1. **那个工具 hook 在哪**：一手文档写着 `DLSS/NGX → D3DMetal → MetalFX temporal scaler → FSR`。
   CrossOver 里的「DLSS」本来就不是 NVIDIA 的 `nvngx.so` —— D3DMetal 自己实现 NGX、
   调 **MetalFX 的时域 scaler**，而那个 hook 只替换时域 scaler 的 `encodeToCommandBuffer:`。
   ⇒ 它作用在**游戏渲染管线内部**，每帧从 scaler 上读 `color(RGBA16F) / depth(R32F) / motion(RG16F) /
   jitter / motionVectorScale / preExposure / reset / depthReversed` + 按 scaler 维护的历史帧。
2. **我们在哪**：SCStream 采的是**窗口服务器合成完之后**的画面 —— 一张 SDR 8-bit sRGB 二维图
   （README「输出 SDR 8-bit」那条）。depth / MV / jitter **一个都拿不到**。
   ⇒ 两个位置差着一整条渲染管线，中期内没有交集。
3. **"能不能喂假数据"** —— 不能，而且这是那个工具**自己踩过的坑**：它的文档里写，两个 scaler 共用一份历史时，
   拿到 `4×4 RGBA8` **占位**运动纹理的那次调用会把当前帧按"零运动"混进历史，运动物体后面就留拖影，
   「输入分辨率越低，网络越信任历史，拖影越长」。我们连占位值都没有。
   ⇒ 编输入 = 拖影，**比现在的 Lanczos 更差**。（自算光流冒充 MV 也不划算：又贵又不准，等于重做一条光流管线。）
4. **本机现状（2026-10-16 实测）**：**M1 Max / macOS 27.0.1 / 未装 CrossOver**（无 bottle）。
   它要求 CrossOver 24+ / Rosetta 2 / Xcode 26 + Metal Toolchain；`auto` 在非 family 10 的 Apple GPU
   落到 scalar 后端，README 自称 "fastest on M5"，**性能数据全来自 M5，M1–M4 未基准**。
   ⇒ 就算想体验，也不是"装个 app 就完事"，且画质未必有笔记说的那么神。
   ⚠️ 笔记里的「即使是**性能模式**画质也不错」指的是 **FSR4 的 preset**，别跟本工具的「性能模式」
   （LSFG 省电着色器）混为一谈。
5. **该走的路**：**空间超分** —— `MetalFX Spatial`（`MTLFXSpatialScaler`，macOS 13+ 系统自带、
   只要一张 color 纹理、`colorProcessingMode = .perceptual`）是下一步（10-12 那篇第 6 节的第 2 步）。
   注意对称性：**MetalFX 自己分空间/时域两个 scaler，能用的恰好是空间那个**，时域那个和 FSR4 一样封死。
6. **FSR4 里唯一对我们可用的部分，早就在了**：它后处理的 **RCAS**（纯空间锐化）≈ 现有 `CASPass`。
   ⇒ 别再往这条路上使劲。

**红线**：不要给引擎/`present()` 硬塞 FSR4 kernel；不要为了试它去装一整套前置条件；
**不要在任何 UI / README 里出现「FSR4」字样**（我们做的是空间重采样 + 锐化，冒称会直接违反
README 第三方来源表与 10-15 验证报告的诚实口径）。

**真要用 FSR4 的正确姿势是叠加、不是集成**：CrossOver 游戏内走 FSR4 提清晰度（游戏管线内，与我们无关），
再用本工具给那个 CrossOver 窗口插帧 —— 两者各管一段，互补不冲突。

### 第十八轮：Magpie（Windows）对照 —— Mac 版窗口超分能做成什么样

用户看到 [Magpie](https://github.com/Blinue/Magpie)，问 Mac 能不能给图片/视频加「DLSS」。
完整清单写进 `Mac版Magpie-算法落地清单-2026-10-16.md`，这里留要点。

1. **先纠正：Magpie 里没有 DLSS。** 它 40+ 种效果**全是空间算法**（Anime4K / FSRCNNX /
   CuNNy / ACNet 是单帧 CNN，FSR_EASU 是近似 ML 的空间算法），没有任何一个要 depth/MV。
   ⇒ **正因如此 Mac 才做得到** —— 与上一轮 FSR4（时域，缺输入）恰好相反。
   另外它是**窗口**超分，处理的是"播放器/图片查看器窗口"，不是图片文件本身。
2. **架构同构**：Magpie = WinRT Capture 抓窗口 → D3D11 shader → 自己的全屏窗口；
   我们 = SCStream → Metal → 贴源穿透覆盖层。**抓取与输出两端做法一致**，
   缺的只是**算法库**（它 40+ 种，我们 2 档）。我们还多一个 Magpie 没有的 LSFG 插帧。
3. ⚠️ **许可红线**：**Magpie 是 GPL-3.0（copyleft）⇒ 绝不从它仓库取 HLSL**，会传染本项目。
   要取**上游原始实现**：FSR1 = `FidelityFX-FSR`(MIT)、Anime4K = `bloc97/Anime4K`(MIT)、
   NIS = `NVIDIAImageScaling`(MIT)、CAS = `FidelityFX-CAS`(MIT)。与 README 许可表口径一致。
4. **落地顺序**：MetalFX Spatial（系统自带、Magpie 没有、只要一张纹理）
   → FSR1 EASU+RCAS（用户最初说的"FSR 那种缩放"本体）
   → Anime4K（用户点名过）→ NIS / FSRCNNX 等。
   加一档 ≈ `ReconstructMode` 加 case + 一个 Metal pass + UI 一项 + 验证一条，与 `CASPass` 同量级。
5. **图片文件（离线放大导出）是另一个形态**，别混进主 App —— 实时覆盖层与批处理的验收标准不同。

**未做**：本轮只出清单，**没动手加档**（等用户确认先做哪一档）；
同图 A/B 判据（质心间距 + 笔画梯度，`dev/verify-quality.swift`）要先立起来再谈"画质提升"。

### 第十九轮：修正 —— 魔改版 Magpie 确实有 DLSS（DLSS-NR），但 Mac 做不了

用户指出 Magpie 能用 DLSS5。**用户是对的，上一轮我漏查了**：只看了官方 `Blinue/Magpie`
（其内置效果清单里确实没有 DLSS），漏了社区魔改版 **`SAOG0721/Magpie`**（"Magpie Experimental"）。

1. **它有什么**：内置效果 `DLSSNR`，另有实验性 DLSS SR / FSR 2 / 3 / 4 / XeSS SR、
   帧生成（DLSSFG / XeSSFG / FSR3FG / NVIDIA VFG）、RTX Video。
   自述：*"Unofficial experimental fork with **colour-only DLSS**, FSR2 and NVIDIA RTX Video integrations"*。
2. **DLSS 5 = DLSS-NR（Neural Rendering）**：随 NBA 2K27 抢先体验版**误打包泄漏**的
   `nvngx_dlssnr.dll`（约 158 MB），NVIDIA 尚未正式发布（SIGGRAPH 2026 预览过）。
   ⚠️ 两个关键属性：**colour-only（只要颜色）** + **同分辨率**（它是"神经渲染"后处理：
   tone / structure / shadow / reflection / glow，**不是超分**）。
3. ⚠️ **这推翻了我上一轮的一个隐含前提**："凡是 AI 的都要 depth/MV" —— 不成立。
   只要模型设计成 colour-only，窗口工具就能喂。**这是本轮最大的认知修正。**
   同理 Magpie 里的时域效果是靠**估算光流**（estimated optical flow）代替真 MV 的 ——
   我上一轮说"自算光流冒充 MV 不划算"，人家在 Windows 上真做了
   （但它自己的 README 也承认"不等于原生游戏内 DLSS/FSR/XeSS 集成"）。
4. **但 Mac 依然做不了**：硬依赖链 = `nvngx_dlssnr.dll`（NVIDIA 专有，不可再分发）
   → NGX 运行时 `_nvngx.dll`（从 NVIDIA **Windows 驱动包**提取）→ Tensor Core(FP8) + CUDA
   → Windows + NVIDIA 驱动 616.56+。Mac 没有 N 卡/驱动/NGX/CUDA。
   有人移植到了 AMD（`DLSS-NR-on-AMD`，拦 NGX API + 把数学翻到 HIP RT），但那是
   **Windows + Adrenalin**，且 **RX 9070 XT 只有 ~33 FPS @1080p**。
   ⇒ **硬件锁是软件锁，但搬到 Metal 等于重做那个 AMD 工程**；再加 M1 Max 无 FP8、
   模型是**未发布的泄漏二进制**（许可灰区）—— 工程量 / 算力 / 许可三条全不划算。
5. **效果本身有争议**（别看广告）：社区反馈**文字瞬间模糊**、看 30 分钟头晕、人脸"越拉越油腻"；
   性能上 4090 在 *Control* 里 −40%（130→82 FPS）、5070 在 *CP2077* 里腰斩（138→68 FPS）。
6. **Mac 的等价物是 Apple 自己的神经引擎路线**（CoreML / Metal 跑开源空间 AI 模型，或 MetalFX），
   **不是 DLSS-NR**。⇒ 落点不变：空间算法档位（见第十八轮第 4 条的顺序）。

**改了什么**：`Mac版Magpie-算法落地清单-2026-10-16.md` 修正 §1 标题与结论口径、
新增 §1b（DLSS-NR 全貌 + 为什么 Mac 不行）、§6 加一条红线。

**教训（值得记）**：查"某工具支持 X 吗"时，**先确认是官方版还是社区分支** ——
这次差点因为只查官方仓库而给出"没有 DLSS"的错误结论。同一个项目名底下可能是两个不同的东西。

### 第二十轮：MetalFX 空间放大档（第三步落地），以及那个一反直觉的翻转

用户：「按你的想法，做一个可以落地的效果」。按 `缩放与画质增强-可行性-2026-10-12.md`
§6 的第 2 步做了 **MetalFX Spatial** 档。

**为什么是它**：MetalFX 分**空间**和**时域**两个 scaler，**只有空间那个只要一张颜色纹理**；
时域那个（以及 FSR4）要深度 + 运动矢量，窗口采集给不出（见第十七轮）。
所以它是这条路上唯一能用的"AI 级"放大器，而且系统自带、零第三方依赖。

**做了什么**：
- `ReconstructMode` 新增 `case metalfx`（另加 `uiTitle`）；
- 新增 `SpatialPass`（`MTLFXSpatialScaler` 封装：准入判定 + 按尺寸复用，失败记原因不静默降级）；
- `present()` 加 ③-A 分支；`CapturePipeline` 加 `spatialPass` / `spatialUnavailable`；
- 下拉项改成**从 `allCases` 生成**（手写字符串数组与枚举一旦错位，
  `reconstructionChanged()` 会按下标选到**别的档**，界面上表现为"选了没生效"）；
- 新增 `dev/verify-metalfx.swift` 并接进 `dev/verify-local.sh`。

**准入判定**（不满足就降级 Lanczos，并在日志里喊一声原因）：
* 必须**真是放大**（输出 > 输入）—— Spatial 是 upscaler，缩小该用 Lanczos；
* **宽高比必须一致**（容差 0.5%）—— MetalFX 只做整体拉伸、不做「等比 + 居中留黑边」，
  硬用会把画面**拉变形**，而变形比糊更糟且当场看不出来；
* 1:1 时不走（没有意义）。

**⚠️ 本轮最重要的发现：这一档**一次都不能翻**。**
1. 第一次按「与 CAS 档对称」写（第一跳就翻），验证脚本**直接判红**：
   `MAE 正比 142.35 / 垂直翻转 97.65` —— 多了整整一次翻转。
2. 第二次改成「第一跳不翻、`flipVertical == false` 时最后一跳补翻」：
   **true 过了、false 反而红了**。数据说明**两种 `flipVertical` 都该"不翻"**。
3. 最终：这一路**完全不做翻转**，两种取值下方向断言全过（区分度 44.7 / 45.0）。

也就是说：`CI → 纹理 → MetalFX → 纹理 → CI → drawable` 这条链相对「关闭」档
**自带一次上下翻转**，恰好把引擎那一次抵消掉。
⇒ 这是 CASPass 那句「uv 取向只能靠实测定，推错过两次」的**第三次复现**，
而且这次多一条教训：**只测一种 `flipVertical` 一定会改错方向**（第二次就栽在这）。
所以验证脚本现在**穷举两种取值**。

**验证脚本的三条判据**（每条都刻意选成能区分 A/B 的）：
1. **准入**：该拒绝的必须拒绝（缩小 / 1:1 / 宽高比不一致）；
2. **尺寸**：中间纹理真的变成输出尺寸（防「参数传了没生效」那类假成功）；
3. **方向**：与「关闭」档的 CI 路径同向，**外加反向注入断言** ——
   要求"翻转那条 MAE 显著更大（> 20）"，否则这条判据可能只是"永远绿"。

**实测（M1 Max / macOS 27.0.1）**：`SpatialPass` 本机可用（96×64 → 192×128）；
准入 3/3、尺寸 2/2、方向 4/4（含区分度）、内容保持 1/1，`PASS actual MetalFX Spatial pass`。

**未做 / 未验证（诚实清单）**：
* **画质 A/B 没做** —— MetalFX 在这类源上比 Lanczos 好多少**没量过**（10-12 文档的清单里就列着）。
  本轮只证明「结构正确 + 方向正确」，**不宣称画质提升**；
  要真下结论得走 `dev/verify-quality.swift` 那套质心间距 / 笔画梯度。
* 真机（真 drawable + 真 LSFG 引擎）上的方向只做过**离线模拟**，没跑 `dev/orient-run.sh`。
* 输出尺寸变大后引擎光流成本按像素数上涨（10-12 §5 量过约 4×），帧率是否达产要实测。
* 苹果文档要求 Spatial 的输入已抗锯齿、无噪点；带锯齿的低清源会被连同锯齿一起放大。

### 第二十一轮：把「输出尺寸」接到 UI + 画质 A/B 实测

用户：「把「输出尺寸」接到 UI，补画质 A/B」。

#### 一、输出尺寸接到 UI

`--output-scale fill` ⇒ 控制窗新增复选框**「按屏幕分辨率重建」**。优先级：**命令行 > 偏好 > 关**。

⚠️ 三条接线注意（都是"不写就静默失效"那一类）：
1. 它走 **`scheduleEngineSwitch()`（重建引擎）**，**不是** `sendLiveSettings()` ——
   输出尺寸一变，drawable 尺寸和引擎的光流工作尺寸都跟着变，属于**引擎级**参数，
   与倍率 / 抓取方式同类，不能像画质那样运行中热更。
2. **`scheduleEngineSwitch()` 里有个"设置已生效"的短路**（只比对 multiplier / performance / mode）。
   必须把 `outputScaleFill == appliedOutputScale` 加进那个比对 ——
   否则勾选后会被判成"设置已生效"直接返回，**静默不生效**（界面点了像没反应，也查不出原因）。
3. `failPendingSession` 的回退分支也要把复选框一起回退，否则界面停在新值、实际跑旧值，
   而且下次再点它会被当成"没变"而不再触发切换。

子进程通过 `--output-scale fill` **明确传参**（不是指望它自己去读偏好），与 `--reconstruct` 同一套口径。

#### 二、画质 A/B（`dev/verify-metalfx-ab.swift`）

320×180 → 640×360（2×），两组测试用例：

| 用例 | 档位 | 平均梯度 | 相对双线性 | 过冲(振铃) |
| --- | --- | --- | --- | --- |
| A · 硬内容 | 双线性 | 4.677 | 1.000 | 0.002 |
| A · 硬内容 | Lanczos | 8.271 | 1.768 | 0.065 |
| A · 硬内容 | **MetalFX** | 13.542 | **2.895** | **0.200** |
| B · 软内容 | 双线性 | 0.459 | 1.000 | 0.001 |
| B · 软内容 | Lanczos | 0.752 | 1.638 | 0.000 |
| B · 软内容 | **MetalFX** | 1.465 | **3.192** | 0.066 |

**读法（**不宣称"更好"**，画质取决于内容）**：
* MetalFX 的**锐度增益明显高于 Lanczos**（约 1.8–2 倍）；
* 代价是**过冲（光晕倾向）**：软内容 0.066、硬内容 0.200（后者是 Lanczos 的 3 倍）
  ⇒ 它是**更激进的锐化型**放大器，内容越"硬"越容易在边缘出黑边白边。

**⚠️ 本轮方法论教训（最值钱的一条）**：
第一版**只跑了「硬内容」用例**（含 4px 周期斜线），MetalFX 过冲是 Lanczos 的 3 倍 ——
但那种图案**已接近 Nyquist**，对**任何**锐利放大器都是最不利的输入。
拿它单独下结论，就是**判据本身偏心**（红线：「判据本身错了比没判据更危险」）。
补上「软内容」用例后结论才完整：**同一个算法在两类输入下的过冲差了 3 倍**。
⇒ A/B 必须覆盖两类输入，而且**必须看图**（数字只是代理）——
硬内容那组的 PNG 里，斜线确实被强化成了突出的亮线，肉眼可见。

**未做**：真实内容（视频帧 / 游戏画面）的对比要屏幕录制权限，留待真机；
两组测试图都是合成的，统计特性与真实画面仍有距离。

### 第二十二轮：打 M4 Air 的测试包，揪出「二进制只能跑 macOS 27」这个静默坑

**起因**：要在另一台 **M4 MacBook Air** 上试 MetalFX，把 `.app` 传到自建的临时文件站，对方下载。
打之前顺手核产物，撞到一个**跟本次改动无关、但从 1.1.x 起就一直存在**的坑。

**坑：`build.sh` 没写 `-target` ⇒ 编出来的包只在 macOS 27 能启动**
* `Info.plist` 里 `LSMinimumSystemVersion` 写的是 **15.0**，而二进制 `LC_BUILD_VERSION` 实测
  `minos 27.0` —— **两边不一致，真正生效的是二进制那个**。
* 原因：`swiftc` 不指定 target 时 deployment target 默认取**构建机系统版本**（这台是 macOS 27）。
  表现 = **在 macOS 15–26 的机器上双击直接报「需要 macOS 27」**，而 plist 那句 15.0 会让人
  以为它是支持老系统的。
* 最阴的是**本机（27）永远测不出来**。也就是说之前发出去的 1.1.x / 1.2.0 / 1.3.0 成品包，
  **全都只能在 macOS 27+ 跑**。

**修法**：`build.sh` 显式加 `-target arm64-apple-macos15.0`（架构固定 arm64 —— LSFG 引擎 dylib
本来就只有 arm64）。实测**零编译错误**。

**为什么下限恰好是 15.0（不是随手挑的）**
* 代码里**一个 `#available` 都没有**，所以目标版本被 API 可用性硬钉死：
  `-target …-macos14.0` 报 **2** 个错、`…-macos13.0` 报 **12** 个错（全是 ScreenCaptureKit 的
  `preservesAspectRatio` / `captureResolution` / `ignoreShadowsSingleWindow`（14.0）、
  `includeChildWindows`（14.2））—— 要再往下就得补守卫，没必要。
* 更硬的一条在 **Swift 运行时**：`libswift_errno.tbd` 里写着
  `$ld$previous$/usr/lib/swift/libswiftDarwin.dylib$$1$10.14.4$15.0$$`，含义是
  **macOS < 15.0 时这些符号来自老的 `libswiftDarwin`，≥ 15.0 才来自新的
  `libswift_DarwinFoundation*` 系列** ⇒ **15.0 正好是这套新运行库存在的起点**。
  压到 15.0 以下反而会撞上「目标系统 dyld 缓存里没有这个库」那类硬依赖（红线里记过 AIME 那次）。
* 结论：15.0 同时是「API 下限之上」+「运行时安全下限」，而且正好和 `Info.plist` 里写的对上。
* M4 Air 出厂就是 macOS 15 ⇒ **这个包在它上面没问题**。

**顺带升版本 1.3.0 → 1.4.0**（`appVersion` + `Info.plist` 的 `CFBundleShortVersionString`，
`CFBundleVersion` 5 → 6）。不升的话在 M4 上**看不出拿到的是哪一版** —— 版本号显示在
**菜单栏 ⚡ 图标点开后的第一行**（`窗口插帧助手 · 4× · v1.4.0`，禁用项）+ 启动日志里，
**窗口标题上没有**（控制窗标题固定是「窗口插帧助手」）。

**打包 + 上传（做法留档）**
* 打包用 `ditto -c -k --sequesterRsrc --keepParent`（`zip -r` 会破签名，见红线 104）。打完
  **解回临时目录再验一遍**：`codesign --verify --deep --strict` 通过、主程序与
  `liblsfg_metal.dylib` 与原包 **`cmp` 逐字节一致**、解出来的二进制 `minos` 仍是 15.0。
* 上传到自建的临时文件站（7,852,342 字节实测 37s 传完）。
* **只信接口返回的 `ok:true` 不够** —— 从**公网 URL 下回来比 sha256**：与本地**完全一致**才算发完。
* 顺手在站点上留了一条**备忘记**：这版新在哪、要求 macOS 15+、
  自签名怎么过 Gatekeeper、MetalFX 要勾「按屏幕分辨率重建」才生效、
  **画面若上下颠倒请回报**（MetalFX 的翻转方向是实测定出来的，M4 上未必同向）。

**未做**：M4 Air 上的真机验证（等对方跑）；MetalFX 画质仍只在 M1 Max 上用合成图量过。

### 第二十三轮：用户实测「完全没区别」→ 整档是死代码，已撤掉

**反馈**（真机跑 v1.4.0）：「测试了一下，几乎没发现有任何区别，按屏幕分辨率重建。
还有另外几个画质切换，也几乎看不出任何区别。」

**结论：不是效果弱，是根本没生效。**

* 根因就一行：`let workResolution = 0`（**硬编码常量**）。它是「采集尺寸」与「输出尺寸」
  **唯一**的差来源 —— `plannedOutputSize(respectWorkResolution:)` 只在 `workResolution > 0`
  时才会算出不同的值 ⇒ **采集尺寸恒等于输出尺寸**。
* 连锁：`needScale`（要不要重采样）恒为 false ⇒ **MetalFX 分支永远不进入（一帧都没跑过）**，
  **Lanczos 重采样也整段被跳过**。于是 4 个画质档里**三档逐像素完全相同**，只有 CAS 真有作用。
* 真实日志佐证（`~/Library/Logs/WindowInterp/app.log`）：每一组启动都是
  `采集 640x400 → 输出 640x400`；`workRes=` 只出现过 `0`；`outputScale=` 只出现过 `1.0`；
  `MetalFX` 出现 **0 次**。

**为什么发布前没抓到（本轮最值钱的一条）**：离线 A/B 把 **320×180 直接喂给 `SpatialPass`**，
证明了「这道 pass 算得对」—— 但**没有一条判据问「App 在什么条件下才会调用它」**。
而那个前置条件（输出 ≠ 采集）今天**永远不成立**。→ 已写成红线 119。

**设计层结论**：这套「输出尺寸 ≠ 采集尺寸」的能力本来就是给**「放大铺满屏幕」**
（10-12 文档 §3 档 3a）准备的，而那是第十三轮明确不做的方向。在「贴住源窗口」这个模型里，
采集**已经是 1:1 原生像素**（= 源矩形 × 屏幕缩放因子，上限 = 面板物理像素）
⇒ **没有任何放大空间**，FSR / MetalFX / DLSS 这类上采样**结构性无用**。

**做了什么（v1.4.1）**

* 删掉 `ReconstructMode.metalfx` + `SpatialPass` 整个类 + `import MetalFX`。
* 删掉 `outputScaleFill` / `outputScaleCheck` / `appliedOutputScale` / `--output-scale`
  （含子进程透传、已生效比对、失败回退），**并把尺寸那三个函数收成一个**
