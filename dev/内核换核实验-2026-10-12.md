# 换核实验报告：能不能用小黄鸭 3.2.2 更新本工具的 LSFG 内核？

日期：2026-10-12（第八轮）
结论一句话：**不能，也没必要 —— 工具里现在跑的内核本来就是 Lossless Scaling 3.2.2。**

---

## 一、你的问题与答案

> 「我桌面有我购买的小黄鸭版本，解压后的文件夹，你看看能不能更新内核」

**答案：那个文件夹里根本没有可以换的内核文件。**

| 你以为的 | 实际情况 |
| --- | --- |
| 「解压出来的小黄鸭文件夹里有内核，换进去就行」 | 那是 **默认分支的 DirectX 包**：只有 `Lossless.dll`（DXBC 着色器）+ `.NET` 运行库，**完全没有 `lsfg-vk.dll`** |

`lsfg-vk.dll`（本工具真正吃的那份着色器包）只存在于 Lossless Scaling 的
**Steam `lsfg-vk` beta 分支**，零售默认分支不提供它。这不是我猜的 ——
是 `liblsfg_metal.dylib` 自己 README 的原话：

> Select the **`lsfg-vk` beta branch** under Properties, Betas: the default branch ships
> only `Lossless.dll`, whose shaders are **DirectX bytecode rather than SPIR-V and
> cannot be used here**.

## 二、但我把整条路挖通并实测了（这部分是真收获）

既然你手上有正版文件，我没有停在「不行」上，而是把引擎的加载机制整个逆向清楚了，
并且**真的用你购买的 3.2.2 造出了一份能跑的 `lsfg-vk.dll`**。

### 2.1 引擎怎么找着色器（以前我们不知道）

`liblsfg_metal.dylib` 里自带的诊断串把规则全暴露了：

```
lsfg-vk.dll
steamapps/common/Lossless Scaling/lsfg-vk.dll     ← 自己去 Steam 找
drive_c/Program Files (x86)/SteamLibrary/Application Support/Steam
WINEPREFIX
No section contains the resource directory
No RT_RCDATA entry in the root directory
Wanted a subdirectory here, got a data entry
Data entry lies outside the resource section
Wanted a data entry here, got a subdirectory
Language directory has no entries
Too few entries in the RT_RCDATA directory
Too few entries in the root resource directory
Optional header is not PE32+
Bad PE header signature
Bad DOS header magic
```

**三条硬规则：**

1. **`LSFGM_DLL_PATH` 只取父目录**，然后固定去找里面名为 `lsfg-vk.dll` 的文件。
   传 `.../Lossless Scaling 3.2.2/Lossless.dll` 时，引擎实际去找的是
   `.../Lossless Scaling 3.2.2/lsfg-vk.dll` → 报 `No shader DLL at the given path`。
   **文件名必须叫 `lsfg-vk.dll`**（这点很重要，做实验时全靠它）。
2. **着色器存在 PE 的 `.rsrc` 资源段里**，类型必须是 **RT_RCDATA(10)**，
   而且引擎会做结构校验（上面那一串 error 就是校验失败的分支）。
3. **引擎按「名字」索取着色器**，缺一个就报
   `Shader '<name>' missing from DLL`，然后**优雅降级**（正常 present，不崩）。

### 2.2 引擎想要的着色器名字表（完整挖出）

```
mipmaps
alpha0 alpha1 alpha2 alpha3
beta0  beta1  beta2  beta3  beta4
gamma0 gamma1 gamma2 gamma3 gamma4
delta0 delta1 delta2 delta3 delta4
epsilon0 epsilon1 epsilon2 epsilon3 epsilon4
generate_8bit
generate_16bit
```

每个 `alpha..epsilon` 名下有 4 个变体（quality/performance × fp16/fp32）：

```
24 个变体名 × 4 + mipmaps + generate_8bit + generate_16bit = 99
```

**⇒ 引擎需要整整 99 个着色器。**

### 2.3 两份文件的真实结构（逐字节取证）

| | 工具里的 `lsfg-vk.dll` | 零售的 `Lossless.dll` |
| --- | --- | --- |
| 大小 | 2,143,232 B | 7,521,280 B |
| `.rsrc` 里的着色器 | 99 条，**全是 SPIR-V** | 300 条：ID 101–302 = **DXBC**（202 条，DirectX）、ID 303–400 = **SPIR-V**（98 条） |
| 资源 ID 方案 | 命名"0" + ID 1..98 | ID 101..400 |
| 版本资源 | **FileVersion 3.2.2.0**、Copyright (C) 2026 | **FileVersion 3.2.2.0**、Copyright (C) 2024 |
| 两边 SPIR-V 逐字节重合 | **1 个尺寸相同（9920），实际内容零重合** | — |

### 2.4 实测：我把零售包的 SPIR-V 灌进了合法的 `lsfg-vk.dll`

工具：`dev/rebuild-lsfg-dll.py`（本次新写）
原理：**以工具里的原文件为 PE 骨架，资源目录树一个字节都不动**，只按顺序重写着色器
数据块并更新 DataEntry 的 RVA/size。这条「最小改动」路线是踩了坑才找到的：

- 第一版我「从零重建整棵资源树」→ 引擎报 `Shader 'mipmaps' missing`
- 第二版改「最小改动」但忘了命名条目的名字串就压在数据区起点前 4 字节 → 同样失败
- 第三版（当前）→ **成功**

三组对照实测（源：`dev/testpattern`，2×，144Hz 主屏）：

| 测试 | 着色器来源 | 结果 |
| --- | --- | --- |
| 基线 | 原始文件原地复制到别的目录 | ✅ `Frame generation runs natively on Metal`，`generated=58/60` |
| **对照组** | 用本工具把**工具自己的 99 个**着色器重灌一遍 | ✅ 正常出帧（**证明工具本身正确**） |
| **实验组** | 用本工具把**你购买的 3.2.2** 里那 98 个 SPIR-V 灌进去 | ✅ **也能跑**：`generated` 逐段递增 49→109→169→229→289→349，零报错 |

**对照组的意义**：如果不做这个对照，第三行「能跑」就不能说明问题 ——
它排除了「是我的工具坏了」这个解释。

### 2.5 可是……两边版本号是同一个

```
工具里的 lsfg-vk.dll :  FileVersion = 3.2.2.0   Copyright (C) 2026
零售的 Lossless.dll  :  FileVersion = 3.2.2.0   Copyright (C) 2024
```

**换过去等于原地踏步。** 而且零售那份的 SPIR-V 只有 **98 个**，
比引擎要求的 99 个**少一个** —— 缺的那一个只能拿工具原来的补上（我的实验里
第 99 格就是原文件的着色器）。这说明零售 `Lossless.dll` 里嵌的那块 SPIR-V
**不是给这个引擎用的完整包**，是它自己 Vulkan 通路的内部资源。

## 三、结论与建议

### 3.1 内核这块：已经是最新的，不用折腾

- 3.2.2 **就是当前最新零售版**（2026-04 更新；changelog 包含
  「修复 LSFG 3.1 Performance 模式影响画质的严重 bug」）
- 工具里的 `lsfg-vk.dll` **版本号就是 3.2.2.0**
- 换核路线**技术上已经打通**（`dev/rebuild-lsfg-dll.py`），
  但**现在没有更新的东西可换**

**什么时候这个工具才有用**：等 Lossless Scaling 出 3.3.x，或 Steam
`lsfg-vk` beta 分支更新到高于 3.2.2 时 —— 那时把新版 `lsfg-vk.dll` 拿过来，
若它已被打包成 PE，直接用 `--engine-env LSFGM_DLL_PATH=<目录>/lsfg-vk.dll` 指过去即可；
若是混在 `Lossless.dll` 里，才需要这个重打包工具。

用法：

```sh
# 最小改动重打包（推荐）
python3 dev/rebuild-lsfg-dll.py --minimal <PE骨架> <新着色器来源PE> <输出>/lsfg-vk.dll

# 不做实验就试：不碰 App 内文件，运行时覆盖
./窗口插帧助手.app/Contents/MacOS/WindowInterp --engine-env "LSFGM_DLL_PATH=/tmp/xxx/lsfg-vk.dll"
```

### 3.2 DLSS 那条路：对本工具**不适用**（已核实，不是敷衍）

查了 `nschlaepfer/Netal`（把 NVIDIA DLSS 的模型在 Apple GPU 上重建执行，MIT）：

| 项 | 事实 |
| --- | --- |
| 形态 | **菜单栏 App + 游戏运行时**，往**支持 DLSS 的游戏**里注入 |
| 必需输入 | 你自备**精确版本**的 NVIDIA DLL：`nvngx_dlss.dll`（SHA256 `c85f971c…`）、`nvngx_dlssg.dll`（`5d5cbf14…`），文件版本都是 `310.8.0.0`。**「同名的更新版本不保证支持」** |
| 已验证场景 | Resident Evil Requiem，**经 CrossOver** 跑通 SR + 神经帧生成 |
| 系统 | App 部署目标 macOS 14，但**当前 game-runtime API 目标是 macOS 26**；参考机 M3 Max |
| 成熟度 | v0.1.0 preview，非一键；SR 还要 4 张标量标定表、FG 要 67 个模型 buffer |

**为什么用不到我们这个工具上**：Netal 拦的是游戏对
`nvngx_dlss.dll / nvngx_dlssg.dll` 的**接口调用**（需要游戏自己调 DLSS，并要
motion vector / depth 等引擎级数据）。而本工具是**纯图像采集**路线
（SCK 抓画面 → LSFG 插帧 → 覆盖层呈现），**没有任何 DLSS 调用可拦**。

顺带把苹果原生那条也核实了：`VTLowLatencyFrameInterpolation` 需要 **macOS 26+**，
本机是 **15.8.1**，用不了；只有 `VTFrameRateConversion`（15.4+，你 `frameinterp`
项目里已经验过）。

⇒ **「给这个工具用上 DLSS」在当前 macOS 16 以前没有可行路径。**

### 3.3 想真正改善画质/帧率/延迟，能动的是这些（引擎自带旋钮）

引擎的选项表也一并挖出来了。这些**全部可以用 `--engine-env` 运行时试**，不用改代码：

| 环境变量 | 作用 | 备注 |
| --- | --- | --- |
| `LSFGM_FLOW_SCALE` | 光流工作分辨率缩放，`0.25`–`1.0` 或 `auto` | **画质/功耗的主旋钮**，算力随它平方变化；你现在日志里是 `0.50`，调到 `0.75`/`1.0` 是画质提升最直接的一步 |
| `LSFGM_PERFORMANCE_MODE` | 换用 performance 着色器组 | 3.2.2 修过它的画质 bug，值得重测 |
| `LSFGM_PACING_MODE` | 节奏模式（日志里默认 `vsync`） | 另有 adaptive 之类 |
| `LSFGM_OVERRIDE_PRESENT_MODE` | 覆盖 present mode | 与 pacing 配合 |
| `LSFGM_PRESERVE_SWAPCHAIN_IMAGE_COUNT` | 保留交换链影像数 | 可能影响延迟 |
| `LSFGM_LATENCY` | 引擎自带延迟统计（p50/p95） | **比我们的截图法省事** |
| `LSFGM_TARGET_FPS` | 输出帧率上限 | 已默认 = 屏幕刷新率 |
| `LSFGM_NO_FP16` | 关半精度 | 画质对照用 |

配置文件也可用：`/etc/lsfg-metal/conf.toml`、`~/.config/lsfg-metal/conf.toml`
（`LSFGM_CONFIG` 可指定）。

**但请注意前七轮已确认的物理约束**（别再重复试）：
- 引擎按**主屏**刷新率排程 → 要插帧的窗口放主屏（你的 Q24T09 144Hz 正好是主屏）
- 延迟 ≈（倍率＋1）个刷新周期（144Hz 实测 2×=21 / 3×=28 / 4×=35ms）
- **源帧率×倍率 ≈ 刷新率**才有收益；满帧源开插帧必然更卡

```sh
cd ~/Documents/WindowInterp

# 1) 造对照组：把工具自己的 99 个着色器重灌一遍（验证工具正确）
python3 dev/rebuild-lsfg-dll.py --minimal \
  "窗口插帧助手.app/Contents/Resources/Native/lsfg-vk.dll" \
  "窗口插帧助手.app/Contents/Resources/Native/lsfg-vk.dll" \
  /tmp/lsfgctl2/lsfg-vk.dll
# 预期：回读 99 个 SPIR-V；与输入一致 = True

# 2) 造实验组：用你购买的 3.2.2 里的 SPIR-V
python3 dev/rebuild-lsfg-dll.py --minimal \
  "窗口插帧助手.app/Contents/Resources/Native/lsfg-vk.dll" \
  "/Users/zxwzz/Desktop/Lossless Scaling 3.2.2/Lossless.dll" \
  /tmp/lsfgret2/lsfg-vk.dll

# 3) 跑（引擎只认父目录里名为 lsfg-vk.dll 的文件，所以必须放目录里）
./窗口插帧助手.app/Contents/MacOS/WindowInterp --autostart \
  --engine-env "LSFGM_DLL_PATH=/tmp/lsfgret2/lsfg-vk.dll"
# 看 ~/Library/Logs/WindowInterp/engine-*.log 里有没有
#   Frame generation runs natively on Metal  /  Shader 'xxx' missing from DLL
```
