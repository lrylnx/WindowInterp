# FSR4 能不能用在窗口插帧助手上 —— 可行性评估

2026-10-16。用户在网上看到一份笔记：

> Mac 使用 FSR4 超分，画质大幅度提高。GitHub 上架了 fsr4-native-macos……安装后选一个容器、
> 点安装，打开容器进游戏，抗锯齿设为 DLSS，此时放大模式就是 FSR4。即使是性能模式，画质也不错。

问：能不能把这个 FSR4 也用上，给 WindowInterp 提画质。

**结论先给：不能。而且这不是"功能还没做"的问题 —— 是输入契约不满足（§2/§3）。
喂不进去的东西编出来，画质会比现在更差。**
但"提画质"这件事本身有解，只是得走另一条路：**空间超分**（§5）。
另外那份笔记跟本工具其实是**两条互不相交的路径**，本机也还没有它要求的前置条件（§4）。

---

## 1. 先纠正一个混淆：FSR4 ≠ 之前说的那种「FSR 缩放」

项目在 `缩放与画质增强-可行性-2026-10-12.md` 里评估过用户提的「小黄鸭那种 FSR 缩放」。
那说的是 **FSR 1.0** —— 纯空间算法（EASU 放大 + RCAS 锐化），**只要一张颜色图**就能跑。
本次问的 **FSR4** 是完全不同的东西：

| | FSR 1.0（小黄鸭的「FSR」档） | FSR4（笔记里那个） |
| --- | --- | --- |
| 类型 | 空间超分（单帧） | **时域超分**（ML，多帧累积） |
| 输入 | 一张颜色图 | 颜色 + **深度** + **运动矢量** + 抖动 + 曝光 + 历史帧 |
| 放大倍数 | 固定 1.5×/2× 等 | 按输出/输入比自动选 preset |
| 实现 | 手写 shader | 14 个 kernel 的神经网络（INT8/FP16） |
| 能不能套我们的采集输出 | **能**（这就是 10-12 那篇的结论） | **不能**（缺一半输入，见 §3） |

所以「FSR4 比同档 MetalFX 好很多」这句是对的，**但换不来给我们用** —— 它的画质正是靠
那些我们拿不到的额外输入换来的。

---

## 2. FSR4 的输入契约（来自该项目一手文档）

`docs/FSR411_INPUT_CONTRACT.md` 开头一句话说明了整条路径：

> The live path is `DLSS/NGX → D3DMetal → MetalFX temporal scaler → FSR`.

也就是：**CrossOver 里的「DLSS」根本不是 NVIDIA 的 `nvngx.so`**，而是 D3DMetal 自己实现 NGX、
再调用 **MetalFX 的时域放大**。那个工具做的事是：

> Хук подменяет только `encodeToCommandBuffer:` у временного скейлера.
> Пространственный скейл, генерация кадров и денойз остаются на MetalFX.
> （hook 只替换时域 scaler 的 `encodeToCommandBuffer:`；空间缩放、帧生成、降噪都留在 MetalFX。）

它每帧从 MetalFX scaler 上读走的字段（一手清单）：

| 字段 | 用途 |
| --- | --- |
| color | 低分辨率颜色，**RGBA16F** |
| depth | 深度缓冲，**R32F** |
| motion vectors | 运动矢量（上一帧位置 − 当前帧位置），**RG16F** |
| jitter | 像素采样偏移，逐帧变化 |
| motionVectorScale / lowResMV / outputResMV | 运动矢量的坐标系与符号约定 |
| preExposure / exposure texture | 曝光（含 SPD 自动曝光） |
| reset / depthReversed | 历史重置、深度方向约定 |
| 历史帧（history / reprojection / recurrent state） | **按 scaler 对象维护**的时域状态 |

文档还专门写了它踩过的坑，很能说明"这些输入不能省"：

> один скейлер получает настоящее поле движения `RG16Float` размером с рендер,
> другой — заглушку `4×4 RGBA8`……заглушка вмешивала текущий кадр в историю с нулевым
> движением, и за движущимися объектами оставался шлейф. Чем ниже входное разрешение,
> тем сильнее сеть доверяет истории, тем длиннее шлейф.
> （有的 scaler 拿到真运动场，有的拿到 `4×4 RGBA8` 的占位纹理；两者共用一份历史时，
> 占位纹理会把当前帧按"零运动"混进历史，运动物体后面就留下拖影。输入分辨率越低，
> 网络越信任历史，拖影越长。）

**这段就是我们的反面教材**：运动矢量喂成占位值 → 时域网络必然拖影。而我们在窗口层能拿到的，
连"占位值"都不如 —— 是完全没有。

## 3. 为什么窗口插帧助手接不上

两条管线放在一起就清楚了：

```
【fsr4-native-macos】作用在「游戏渲染管线内部」
游戏 → DLSS 调用 → D3DMetal/NXG → MetalFX temporal scaler
                                    ↑ hook 在这里换成 FSR4
        （游戏自己提供 color / depth / MV / jitter / 历史）

【窗口插帧助手】作用在「窗口合成之后」
源窗口 → SCStream 采集 → CIImage(8-bit sRGB) → Lanczos/CAS → drawable → LSFG → 覆盖层
                          ↑ 这里只有一张合成好的 2D 图，depth/MV/jitter 一个都没有
```

采集这一层是**窗口服务器合成完的结果**：一张 SDR 8-bit sRGB 的二维图像（README「不支持 DRM / 输出 SDR 8-bit」那条）。
深度缓冲、运动矢量、逐帧抖动矩阵这些**只存在于源 App 自己的渲染管线里**，跨进程拿不到。
LSFG 引擎内部确实在算光流，但那是专有二进制的内部状态，输出的是插帧后的画面，不是可读的 MV 纹理。

### 三个"看起来能绕"的想法，以及为什么不绕

| 想法 | 为什么不行 |
| --- | --- |
| 给 depth/MV 填 0 或常数 | 就是上面那段拖影的成因。时域网络没有运动信息时只能靠历史累积 ⇒ 运动场景糊 + 鬼影，**比现在的 Lanczos 更差** |
| 用自算光流冒充 MV | 要额外一整条光流管线（正是 LSFG 在做的、且更贵），精度还远不如游戏引擎直接给的 MV；工程量大、结果不确定 |
| 从 LSFG 引擎里把光流场捞出来 | 引擎是专有二进制，没有输出 MV 的接口；我们只能看到它输出的**帧** |

⇒ FSR4 这条路在**架构上就不通**，不是工程量问题。

另外顺带澄清：笔记里的「即使是**性能模式**，画质也不错」，那个"性能模式"是 **FSR4 的 preset**
（按输出/输入比自动判定 quality/balanced/performance）。这跟本工具的「性能模式」——
LSFG 引擎的省电着色器（README：轻量着色器降低 GPU 开销）——**是两回事**，别混。

## 4. 本机现状核对（2026-10-16 实测）

| 项 | 实测值 | 对 fsr4-native-macos 的影响 |
| --- | --- | --- |
| 芯片 | **Apple M1 Max**（10 核：8P+2E） | 它不是 M5/family 10。该项目 `auto` 在非 family 10 的 Apple GPU 上落到 **scalar INT8** 后端（同一模型、更慢）；README 自称「fastest on M5」，**没在 M1–M4 上做基准** |
| 系统 | macOS **27.0.1** | 满足它要求的 macOS 26+ |
| CrossOver | **未安装**（`/Applications`、`~/Applications` 都没有，也无 bottle 目录） | **前置条件不满足** —— 它整条路径依赖 CrossOver + D3DMetal，没装就没有"容器"可选 |
| Xcode 26 + Metal Toolchain / Rosetta 2 | 未核对 | 它要求 `xcodebuild -downloadComponent MetalToolchain` |

⇒ 就算用户想体验笔记里那套，也**不是装个 app 就完事**：得先有 CrossOver 24+、Rosetta 2、
Xcode 26 + Metal Toolchain，而且能在 M1 Max 上跑成什么样，官方没给数字（它自己的性能数据全是 M5）。

**更要紧的是**：那套东西服务的是「用 CrossOver 跑 Windows 游戏」这个场景。而 WindowInterp 服务的是
macOS 窗口（浏览器视频、播放器、窗口化 App/游戏）。**用户当前没装 CrossOver，说明他未必在那个场景里。**

## 5. 那"提画质"到底该怎么做 —— 空间超分

FSR4 用不了，但"放大重建"这一环是能做的，只要选**不需要 depth/MV 的空间算法**。
10-12 那篇已经把候选列全了，这里按"能不能真的落地"重排：

| 候选 | 依赖 / 许可 | 需要 MV/depth？ | 定位 |
| --- | --- | --- | --- |
| **CAS**（已实现） | 自写 Metal pass | 否 | 纯锐化，当前「画质」档就是它 |
| **MetalFX Spatial**（`MTLFXSpatialScaler`） | **macOS 13+ 系统自带，零第三方** | **否**（只要一张 color 纹理） | **建议的下一步**：苹果版"FSR"，`colorProcessingMode = .perceptual` 适配我们全链路 sRGB |
| **FSR 1.0**（EASU + RCAS） | 开源，要手写 Metal 版 | 否 | 与 MetalFX Spatial 定位重叠，二选一并做 A/B |
| **Anime4K** | MIT（另有 Metal 移植） | 否 | 动漫/线稿/字幕这类源最合适 |
| ~~FSR4~~ | 见 §2/§3 | **是（拿不到）** | **不可用** |
| ~~MetalFX Temporal~~ | 系统自带 | **是（拿不到）** | **不可用**（同一类约束） |

注意最后两行的对称性：**MetalFX 自己就分成空间和时域两个 scaler，能用的恰好是空间那个。**
这也从侧面印证了 §3 的判断 —— 时域超分这条路对"只看得到合成画面"的工具是封死的。

**FSR4 里唯一对我们可用的东西，其实早就在了**：它后处理那个 **RCAS**
（Robust Contrast Adaptive Sharpening，纯空间、只要一张纹理）。当前 `CASPass`
（`main.swift:1001` 附近）做的正是同一类对比度自适应锐化。文档也如实写着"没有把它冒称为完整 AMD FSR"。

### 落地步骤（沿用 10-12 那篇第 6 节，已完成第一步）

1. ~~把 `present()` 里那道双线性换成 CAS，解耦 `renderSize` / `captureSize`~~ —— **已完成**（v1.3.0）
2. **下一步**：把 CAS 换成 / 并列一个 **MetalFX Spatial** 档，做 A/B 再定默认
3. 可选：加 Anime4K 档
4. 并行决定：要不要"观影铺满"档（档 3a，零输入风险）

### 验收方法（不能靠肉眼）

复用 12 轮那套：确定性测试图 + 质心间距测尺度 + 笔画梯度测锐度（`dev/verify-quality.swift`）。
新增 MetalFX 档时必须同图 A/B，并**先证伪"新档什么都没变"**（否则会像 LSFG 那样把"没生效"当成"没提升"）。

## 6. 明确不要做的三件事

1. **不要给 LSFG 引擎或 `present()` 硬塞 FSR4 的 kernel** —— 输入不满足，必然拖影（§3）。
2. **不要在没有 CrossOver 的机器上为了试 FSR4 去装一整套前置条件** —— 场景不匹配（§4）。
3. **不要把"FSR4"这个名字写进 README 或 UI** —— 我们做的是空间重采样 + 锐化，
   冒称 FSR4/FSR 会直接违反项目已有的诚实口径（README 第三方来源表 + 10-15 验证报告的自述）。

如果**确认**用户要玩 CrossOver 里的 Windows 游戏，那正确组合是两者**叠加**，各管一段：

```
CrossOver 游戏 ──[游戏内 DLSS → fsr4-native-macos]──> FSR4 提清晰度
                        （游戏渲染管线内，与我们无关）
                                    ↓
                        CrossOver 窗口 ──[WindowInterp / LSFG]──> 插帧提帧率
```

互补、不冲突。但这是"配置 CrossOver"，不是"改 WindowInterp 的代码"。

## 7. 未验证 / 风险（诚实清单）

- fsr4-native-macos 在 **M1 Max 上的真实速度与画质，未实测**（该项目的性能数据全部来自 M5；
  M1–M4 走 scalar 后端，属未基准区间）。笔记里"画质比 MetalFX 好很多"未经本人验证。
- 我**没有实测** FSR4 喂零运动矢量的输出画质 —— §3「必然拖影」是该工具一手文档里
  占位纹理那段的**推论**，方向可信，但具体退化程度没量过。
- MetalFX Spatial 在我们这类源（游戏 720p 带锯齿输出）上比现有 CAS 好多少，**没量过**，
  要做 A/B 才能定默认档（同 10-12 那篇的诚实清单）。
- 本机是否装了 Xcode 26 + Metal Toolchain / Rosetta 2，本次未核对（不影响 §3 的结论）。
