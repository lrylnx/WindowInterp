# 自动倍率（按窗口帧率自适应）—— 设计、实现与实测

日期：2026-10-12（第十一轮）· 机器：M4 / macOS 15.8.1 / 主屏 Q24T09 2560×1440@144Hz
代码：`main.swift`（`AutoMultiplierPlanner` + `AppDelegate` 的「自动倍率」段）· 版本 `1.1.0-auto1`

---

## 一、为什么需要它

同一块 144Hz 屏上，「最合适的倍率」会随**源窗口真实帧率**变化 —— 这是第十轮普查
（`dev/优化空间普查-2026-10-12.md`）挖出来的，但当时只给了「手选建议」，手选不可能跟着源变。

三个互相拉扯的量：

| | 规律 | 实测证据 |
| --- | --- | --- |
| ① 输出帧率 | 越贴近刷新率 R 越顺；超出 R 的帧**显示不出来** | 5× 实测 `source=420 → generated=1676`，输出 145fps ≈ 144Hz |
| ② 节奏抖动 | `late ≈ \|R/out − round(R/out)\|`，out = 源帧率 × 倍率 | 2× = 26%、3× = 3.8%、5× = 0.4%（同一源的 `display intervals … late=`） |
| ③ 源信息损失 | 采集上限 = R÷倍率 ⇒ 倍率越高，源帧被砍得越狠 | 5× 把 60fps 游戏钳到 29fps（`effectiveCaptureFPS`） |
| ④ 延迟 | 高刷屏上 =(倍率+1) 个刷新周期 | 21 / 28 / 35ms（2/3/4×） |

②还解释了一个反直觉现象：**高倍率反而更顺** —— 因为采集被钳到 R÷倍率 后输出自然贴住 R。
所以「用户举例 24fps 视频原片更流畅、插帧更卡」，根因多半就是固定倍率撞上了 ②/③。

⇒ 结论：**没有「全能倍率」，只有随源帧率变的取舍**。这只能靠自动化。

## 二、模型（可离线验算，不用先跑再骂）

给定源帧率 S 与主屏刷新率 R（**引擎按主屏排程**，实测输出放 60Hz 副屏也照主屏算）：

```
采集上限 cap(m)   = max(24, round(R / m))          ← 与 effectiveCaptureFPS 同式
有效源   S_eff(m) = min(S, cap(m))
输出     out(m)   = min(S_eff(m) × m, R)
节奏抖动 pace(m)  = |R/out − round(R/out)|          ← 与引擎自报 late 占比线性吻合
源损失   starve(m)= max(0, S − R/m) / S
延迟     lat(m)   = (m+1) × 1000 / R

评分 = 100×(out/R)                       ← 帧率完成度，权重最大（用户要丝滑）
       − 45×pace                          ← 节奏抖动
       − 25×starve                        ← 源信息损失
       − 15×clamp((lat−20)/60, 0, 1)      ← 延迟（20ms 起罚、80ms 罚满）
       −  6×max(0, m−4)                   ← 生成负担（每源帧生成 4 张以上开始扣分）
```

移除「输出必然超出 R」的档位（算了也显示不出来）。离线验算：

```bash
./窗口插帧助手.app/Contents/MacOS/WindowInterp --auto-dry-run --source-fps 60 --refresh-hz 144
```

144Hz 上的首选结果：

| 源帧率 | 首选 | 输出 | 抖动 | 源损失 | 延迟 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 24fps | **6×** | 144 | 0% | 0% | 48.6ms | 24×6 = 144 整除，零抖动零损失（代价：延迟最高、每源帧生成 5 张） |
| 30fps | 5× | 144 | 0% | 4% | 41.7ms | |
| 40fps | **4×** | 144 | 0% | 10% | 34.7ms | ← 用户当时手选 3× 恰好是「20% 抖动」的坏档 |
| 48fps | 3× | 144 | 0% | 0% | 27.8ms | 144/48 = 3 整除，完美 |
| 60fps | 3× | 144 | 0% | 20% | 27.8ms | 2× 只能出 120fps 且抖动 20% |
| 72fps | 2× | 144 | 0% | 0% | 20.8ms | 144/72 = 2 整除，最好的一档 |

## 三、流程与硬闸门

**两段式**（倍率是引擎的**进程级环境变量**，改它只能重启进程 ⇒ 每换一档 = 一次 relaunch，
状态通过 `--auto-*` 参数沿重启链传递）：

1. **探测轮**：先用 2× 跑一个观察窗（默认 10s），量出源窗口真实帧率 S。
   （2× 的采集上限 = R/2 = 72fps，够放行绝大多数源。`--test-window`/`--multiplier` 都默认关掉自动。）
2. **规划**：算出候选阶梯（首个 = 首选，后面是**单调递减**的降档序），写进 `--auto-plan`。
   首选恰好就是探测轮那一档（2×）时**不重启**，直接定档。
3. **试档轮**：跑一个观察窗，用引擎自己的遥测判定；不达标就往阶梯下一档降。

**判定**（`autoVerdict`，全部取实测，不做主观猜测）：

| 判据 | 阈值 | 依据 |
| --- | --- | --- |
| 输出没到规划值 | < 85% | 这条**已涵盖**「生成比例不足」：`输出 = 源帧率 × Δtotal/Δsource` |
| 节奏抖动 late 占比 | > 15% | 实测 3× = 3.8%、2× = 26% |
| 引擎丢帧 **且** 输出没到规划值 | dropped > 0 | 真的算不过来 |

**样本不够就不判**：探测轮要 ≥2 条样本、判定轮要 ≥3 条；硬超时 3 倍观察窗才放弃。
采不到样本一律「保持当前档」，**绝不当成「很好」**（红线：读不到 ≠ 没有）。

**防失控**：重启额度（`--auto-credit`，默认 6，用尽即保持）、重规划上限 2 次、
源帧率漂移检测（偏离 ≥40% 且连续 ≥20s 才重探）、静止画面不硬猜（反复重试观察）、
阶梯走完即止。

## 四、实测验证（M4 / 测试源 `dev/testpattern --ruler` 640×400 / 144Hz 主屏）

| 场景 | 手段 | 结果 |
| --- | --- | --- |
| 主链 | `--auto-force-source 60 --auto-probe 5` | 探测（实测 69fps）→ 阶梯 → **2× → 3×** → 定档 3×（样本 4、源 46、输出 138、抖动 3.4%） |
| 降档链 | `--auto-fail-first 2`（故障注入） | 3×（注入失败）→ 4×（注入失败）→ **5× 真实判定通过** → 定档 5×（输出 145、抖动 0.6%、dropped=0） |
| 额度闸门 | `--auto-credit 3 --auto-fail-first 20` | 6→5→4→3，额度用尽 →「保持 4×」，无死循环 |
| 单调降档 | `--auto-force-source 24` | 阶梯 `[6,5,4,3,2]`，一路往下不再回头 |
| 静止画面 | `dev/testpattern --static`（源整幅不动） | 采集侧 `complete=1 idle=2728`（真不出帧）→ 引擎零统计 →「探测失败（样本 0 条）→ 保持 2×」，每 13s 重试一次 |
| 真实默认路径 | `--auto-multiplier`（不伪造源） | 量到 69fps → 阶梯 `[2]` → **定档 2×，零重启** |

新工具/开关（都留在仓库里，下次改动可以复跑）：

```bash
# 1) 离线核对打分模型（不动引擎、不开窗）
…/WindowInterp --auto-dry-run --source-fps 60 --refresh-hz 144 [--auto-max 4]

# 2) 端到端自适应（确定性：源帧率由参数指定）
…/WindowInterp --window-id <源窗口> --autostart --test-window \
    --auto-multiplier --auto-force-source 60 --auto-probe 5 [--auto-fail-first N] [--auto-credit N]

# 3) 静止画面负向验证
./dev/testpattern --static --x 40 --y 300 --width 640 --height 400 --seconds 70
```

## 五、测试过程中抓到并修掉的四个问题（全部是「看起来对、实际是错的」）

**① 判据误杀：`worker p95 > 2.5 个刷新周期`（已撤除）**
5×/620×400 时引擎自报 `worker_ms = 5.5/19.8`（p95 是 6.9ms 预算的 2.9 倍），于是被判定
「插值网络跑不赢」而降档。但**同一份日志的客观结果是**：`late = 1/240`（0.4%）、
`dropped = 0`、输出满产 145fps —— 那是客观表现**最好**的一档。
p95 只是瞬时尖峰（p50 仅 5.5ms）。⇒ **代理指标不能压过真实结果**（项目红线），
该判据降级为「只写日志、不参与判定」。修掉之后 5× 正常定档。

**② 死循环：样本不足时把样本清空了**
`defer` 在「等样本」这条 return 路径上也会执行 ⇒ 变成
「攒不够 → 清空 → 重新计时 → 又攒不够」。5× 时引擎每 60 个源帧才写一条统计（≈2.1s），
3 条要 ~6s，永远攒不到。**症状是日志静默 47 秒、界面停在「观察中」，看起来像卡死**
（一个字都没写进日志，是最难查的那种）。修法：时间未到或样本不够就 `return` **不清空**，
只在硬超时（3 倍观察窗）才放弃。

**③ 同口径错误：拿被钳过的观测值比没钳的规划值**
4× 时日志报「试档期间源帧率变成 35fps（规划时 60）→ 重新探测」—— 但真实源是 69fps，
35 只是被 4× 的采集上限（36）钳过的读数。这是**测量学错误**，不是策略问题。
修法：加 `autoExpectedSourceFPS()`，期望值先按当前倍率的采集上限钳一次再比。
（`autoCheckSourceDrift` 有同一个毛病，一并修了。）

**④ 降档序不单调：越降越激进**
按评分排的候选序是 `[3,4,5,2,6,8,10,12]`，从 2× 再取「下一档」就跳到 6×/8×/10× ——
那是**升档**。实测一路爬到 8×（采集被钳到 24fps、输出 192fps 全是废帧）才卡住。
修法：阶梯 = `[首选] + {倍率更低的档，按倍率从高到低}`，降档严格单调递减。

## 六、已知限制

- **高倍率下「源有没有变」测不出来**：采集上限把源帧率钳住后，改内容前后读数都被钳到
  同一个上限（例如 4× 时永远读到 ~35fps），漂移检测天然失明。所以菜单里留了一个
  「自动倍率 ⟳ 立即重新探测源帧率」的手动出口。
- **源帧率高于 R/2 时只能量到 R/2**：探测轮跑 2×，采集上限 = 72fps（144Hz）。
  对 100fps 以上的源会低估，但结论（选 2×）仍然正确。
- **误差界**：判定要求输出 ≥85% 规划值，源本身在场景间抖动 15% 以内不会误判；
  更大变化走「重新探测」而不是「降档」。
- **高倍率的补帧质量本轮没做主观评测**：24fps 在 144Hz 会被选到 6×（=144fps 零抖动、
  源零损失，但每源帧生成 5 张）。觉得补帧痕迹重就用 `--auto-max 3` 或 `4` 设上限
  （实测 40fps 源在 `--auto-max 3` 下会改选 3×）。

## 七、命令行参考

| 参数 | 作用 |
| --- | --- |
| `--auto-multiplier` / `--no-auto-multiplier` | 开/关自动倍率（界面弹窗第一项、菜单勾选、控制窗复选框同效） |
| `--auto-max <n>` | 自动倍率上限（0 = 不限，交给物理上限 `floor(R÷24)`） |
| `--auto-probe <秒>` | 每档观察窗（默认 10s；引擎每 60 源帧写一条统计，太短会量不到） |
| `--auto-credit <n>` | 一条自适应链最多重启几次（默认 6，防死循环的硬闸门） |
| `--auto-force-source <fps>` | 诊断：跳过探测，直接按这个源帧率规划 |
| `--auto-fail-first <n>` | 故障注入：把前 N 次判定故意判成不达标（用来验降档路径） |
| `--auto-dry-run` | 只打印规划表就退出（配 `--source-fps` / `--refresh-hz`） |
| `--multiplier <n>` | 显式手选 ⇒ **自动让位**（测量脚本不受影响） |

**默认是开的**（`UserDefaults["autoMultiplier"]` 未设置过时为 true）。
手选任何一档倍率（弹窗/菜单/`--multiplier`）即视为放弃自动。
